# Firecracker 三把安全锁 · seccomp / cgroup / chroot

## 背景：为什么 guest 强隔离了，还要管 Firecracker 自己

KVM 强隔离（VMCS 管特权、EPT 管内存）保护的是「guest 之间」「guest ↔ host」的 CPU/内存边界。

但 Firecracker 自己是宿主上的普通用户态进程，模拟设备时要调 `open/read/write/ioctl`。若 guest 通过设备漏洞攻破设备模拟代码，进程被劫持，就能以 Firecracker 身份作恶。

所以 Firecracker 给自己套三把锁：**就算进程被攻破，也干不了什么**。

## 第一把：chroot = change root（改变根目录）

管：文件系统视野。把进程的根目录换成子目录，外面的文件系统看不见也碰不到。

例子：每台 microVM 一个专属小目录，只放 rootfs 镜像 + 配置，chroot 进去，攻破后也摸不到宿主 `/etc/shadow`。

> chroot 本身不是严格安全边界（root 可逃逸），Firecracker 是「降权 + chroot + 其他隔离」组合用，属纵深防御的一层。

## 第二把：seccomp = secure computing mode（安全计算模式）

管：系统调用。用 BPF（Berkeley Packet Filter，伯克利包过滤器）做 syscall 白名单：每次 syscall 内核先问「在白名单里吗」，不在就当场杀进程。

例子：Firecracker 只放行 `ioctl/read/write/mmap/poll/epoll` 等极少数，禁 `execve/fork/open` 等。guest 攻破设备代码想 `execve` 起进程，seccomp 直接杀掉。

> 这是「最小攻击面」的硬实现：不是防住攻击，而是攻击成功也废了。

## 第三把：cgroup = control groups（控制组）

管：资源用量。把进程划进一个组，给组设 CPU/内存/磁盘 IO/网络上限，内核调度器按上限掐它。

例子：每台 microVM 一个 cgroup，限制 1 CPU、512MB 内存。一台 guest 疯跑也不拖垮其他租户——正对应 FaaS（Function-as-a-Service，函数即服务）「每租户一台 microVM」的场景。

## 收束：各管一维

| 机制 | 全称 | 管什么 | 一句话 |
|---|---|---|---|
| chroot | change root | 文件视野 | 根目录换成小目录，看不到外面文件 |
| seccomp | secure computing mode | 系统调用 | syscall 白名单，非白名单即杀 |
| cgroup | control groups | 资源用量 | 限制 CPU/内存/IO 上限 |

加上 [[04-硬件隔离与软件隔离]] 里的 namespace（命名空间，隔离「能看见哪些资源」），凑齐 Linux 容器/沙箱的「软件隔离全家桶」。

## 最终分工图景

> KVM 给「CPU + 内存」强隔离（硬）；三把锁给「Firecracker 自己进程」轻收口（软）。强隔离挡 guest 逃逸，软收口保证模拟层被攻破时破坏力被锁死。这就是 Firecracker「又快又安全」的完整拼图。
