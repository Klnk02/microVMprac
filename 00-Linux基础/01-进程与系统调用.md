# 进程与系统调用

## 一条命令背后：fork + exec

在 shell 里敲 `ls` 回车，大致发生：

1. shell 解析命令、沿着 `PATH` 找到 `/usr/bin/ls`；
2. `fork()` 复制出一个**子进程**；
3. 子进程里 `execve()` 用 `ls` 的代码**替换**自身地址空间；
4. `ls` 运行中调用系统调用，让内核替它读目录。

> [!note] 关键区分
> `ls` 是**用户态程序**，内核里没有「ls 这个功能」。内核只提供一批通用系统调用，`ls` 通过它们间接让内核干活。

## 怎么「陷入」内核

- x86-64 上不是靠「通用中断」，而是专门的 `syscall` 指令。
- **系统调用号**放在 `RAX`，参数放在 `RDI / RSI / RDX / ...`。
- CPU 执行 `syscall` 时一气呵成：CPL 3→0、跳到内核入口 `entry_SYSCALL_64`、保存返回地址（`RIP→RCX`、`RFLAGS→R11`）。
- 内核用 `RAX` 里的调用号索引 `sys_call_table`，分发到真正干活的函数。

`ls` 列目录用的系统调用是 `getdents64`（glibc 的 `readdir` 就是包着它），不是 `open`/`read`。

## 为什么用户态不能直接跳进内核

相关概念见 [[特权级与地址空间]]。简言之：不是「内核不在你的地址空间里」，而是权限（特权级）不允许。
