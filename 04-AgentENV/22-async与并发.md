# 第22课：async、等待与取消

2026-11-13 第一轮。通用异步机制与io_uring普通单次READ教学模型，不作为AgentENV已审计取消实现；无取消实验。理解目的优先于面试表达。

## 1. 三个生命周期

任务是运行时管理的工作状态，线程是宿主调度的执行单位，底层IO是内核/设备执行的操作。async函数返回/挂起、工作线程可处理其他任务、底层IO实际完成需分别判断。任务await未就绪且正确注册唤醒时可挂起，运行时线程才有机会推进别的任务；同步PVM若直接在任务中调用仍占用当前工作线程直到返回，可能运行也可能内核阻塞。

## 2. 取消的时间线

假设t=0提交READ到B，t=5ms上层超时，t=8ms底层正常完成。上层t=5ms可根据接口策略报告超时，但IO管理者需继续持有B和操作身份、消费最终结果，再释放资源。超时不等于底层终止，不证明外部副作用没有发生。

取消尚未提交的工作与取消在途IO不同。已提交时按API请求取消，并处理取消与正常完成竞态。教学例使用原READ user_data=42、取消操作自身user_data=99，区分目标请求和取消命令的CQE，不能只凭收到任意CQE释放B。

## 3. io_uring取消结果

io_uring_prep_cancel按原操作user_data等条件找目标。单请求取消成功有明确语义，原请求完成也会发布；一般管理方式是收齐并关联原请求的终态结果，确认无访问后再回收buffer。-ENOENT表示未找到目标，可能原请求已完成或标识错误；-EALREADY表示已推进到难以取消的阶段，原请求完成可能尚需等待。不能用取消失败断言原IO失败，完成也不能证明调用者已消费结果。这里限于普通单次READ，不泛化到multishot/零拷贝通知等其他寿命约定。

## 4. 代码组织

将用户请求等待与在途IO拥有权分开：请求持等待/取消入口，IO管理对象拥有buffer、身份和完成处理职责，直至底层终态并释放。在途操作管理应有并发上限，避免超时后后台工作无限增长。仅丢弃句柄可能分离后台任务而非取消，具体语义需按运行时确认。

Tokio文档示例：丢弃JoinHandle会detach已派生任务；abort也不是强行中断任意同步代码，已开始的spawn_blocking任务不能通过abort终止。这里只用来解释任务/线程/操作边界，未核对AgentENV各处是否采用这些API。

2. READ=42已提交，取消操作=99返回-ENOENT，能否立即断言读取失败并回收buffer？还需核对什么？
