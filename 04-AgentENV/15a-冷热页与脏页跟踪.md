# 补充课：冷热页、驻留与脏页跟踪

2026-11-13 用户要求在第25课前补充。关联第13—18课、A5性能。通用内存管理/KVM机制与已核对AgentENV范围消费者分开，无实际页访问或dirty日志实验。

## 1. 三个独立维度

冷热表示指定观察窗口内的访问活跃度，可分读热/写热；驻留表示指定内存层当前是否有实际页面；脏表示相对某个基线或写回目标需要记录的写入状态。热页可只读且干净，冷页可在较早时刻写过但尚未捕获而脏，冷数据也可仍驻留。热数据、缓存热和CPU硬件cache命中要按层分别说。

## 2. 识别冷热

访问时间窗口、阈值、采样粒度与代价必须明确定义。应用可记录键/文件访问，Guest OS可观察Guest进程页，Host可观察宿主映射/物理页；不能仅按Firecracker进程的常规用户访问统计保证覆盖所有Guest访存。Linux idle tracking支持标记页并观察后续访问，DAMON用区域采样/聚合估计访问模式；依赖内核配置、权限、跟踪后端，虚拟化场景必须验证覆盖与Guest/KVM信号，不直接套普通进程结论。Accessed位表示一段时间是否访问，单个置位不提供精确次数；清除/采样可能影响其他子系统或翻译缓存。

## 3. 四类“脏”与记录

Guest文件页dirty相对于Guest文件系统写回；Guest RAM snapshot dirty相对于跟踪epoch/父快照；Host层文件page cache dirty相对于其Host写回对象；OverlayBD writable upper记录逻辑块修改。Guest fsync可推进磁盘写回，但Guest RAM仍可能相对父快照已修改。位图只记录页号/写历史，数据需另外读取。

KVM开启memslot dirty logging可跟踪Guest RAM写入，GET_DIRTY_LOG按slot返回位图，bit i对应slot中的第i页；标记与清除语义依能力而异，有手动保护/清除与dirty ring等模式。硬件辅助/写保护等机制依架构配置；VMM设备后端直接写Guest RAM的覆盖也需软件正确计脏，不能只追踪vCPU写入。

## 4. 假设六页增量

跟踪周期内，P0反复读、P1写后不再访问、P2改后恢复原字节、P3仅读过一次、P4反复写、P5未访问。假设只这三页发生相关写入，dirty bitmap为[0,1,1,0,1,0]。P1可冷且脏，P2字节与基线相同仍可能dirty；P0热且未写。每页4KiB时三页共12KiB是所选页的逻辑数据量，不保证压缩输出或物理IO量12KiB。

## 5. 脏页处理与一致性

增量快照需要稳定基线、正确epoch、覆盖所有相关写入源，协调暂停/在途设备写入等并取得最终集合，再读取数据、生成层与索引并配套VM状态发布。不能以“冷”跳过仍必需保存的脏页，也不能直接在修改继续进行时随意读位图并清零，避免丢下一周期写入。在线预拷贝可在迭代中重复捕获再脏页，最终收敛/暂停阶段仍需明确。

Guest文件脏页写回、RAM增量快照保存、Host文件写回三条路径分别讨论。匿名私有RAM不能不加区分地写回原只读快照；内存回收需按匿名/文件、可重建性、swap和引用等条件处理，不能用冷热或单个dirty位直接决定删除。

恢复阶段可预取预测会用到的热数据、按需加载其他页，但需要的逻辑内容仍须可恢复。本课程AgentENV固定基线中已核对dirty/present范围→PVM→OverlayBD层的消费链，实际范围生成、清除时序及配套Firecracker映射需继续单独核验。

## 自测与接续

### 2026-11-16：设备后端也会修改Guest RAM

以宿主软件模拟虚拟网卡为例：Guest预先发布接收buffer，FC设备后端把收到的包写进该buffer，修改的是Guest RAM。Guest/vCPU的store走GVA→GPA→EPT→HPA；FC用户态通过HVA写同一后备页走宿主页表，不经过Guest EPT。因此不能仅靠EPT写保护覆盖所有RAM写入，VMM需对设备写入、队列完成记录等正确软件计脏，并在捕获前协调相关写入与收集记录。概念上最终集合包含KVM记录与VMM软件记录；真实数据结构、记录粒度和合并时机按实现核验。

上游当前[Firecracker persist.rs](https://github.com/firecracker-microvm/firecracker/blob/main/src/vmm/src/persist.rs)的create_snapshot在保存内存前调用device_manager.commit_dirty，注释说明设备写过的队列页会延后汇入dirty bitmap，避免数据路径争用。这是本轮核对的上游例证，不证明AgentENV配套版本完全相同。无新VM实测。

### 追加：写保护发现首次写入

2026-11-13 用户三题均给出正确判断，未独立解释原因。继续采用x86/EPT写保护教学模型：Guest页表允许写，KVM为跟踪暂时撤去二阶段页写权限，并按协议维护相关TLB有效性；首次Guest写触发EPT violation，KVM识别跟踪保护、记录页脏、按实现恢复写入条件并让写操作完成。后续本周期写该页通常无需为每次写再退出。下一轮需正确重置记录并重新启用跟踪，而非仅随意清位。该退出可在KVM内核处理，不必让KVM_RUN返回用户态。跟踪标脏可能早于指令重试真正完成，属于保守记录，不能理解为保存了新内容。

单页dirty只记录写发生，不说明修改次数或偏移，不直接给出热度，也不自动触发数据快照。硬件辅助可提供页表脏位等线索，具体收集/同步/清除方式依硬件和KVM能力，脏位与写保护不是所有部署一律使用的唯一路径。VMM直接用HVA写Guest内存仍需软件覆盖计脏。来源：[KVM_CLEAR_DIRTY_LOG与重新启用跟踪](https://docs.kernel.org/virt/kvm/api.html#kvm-clear-dirty-log)。

### 追加：何时开启，怎样定位并收紧EPT

2026-11-13 核对Linux v6.14 virt/kvm/kvm_main.c、arch/x86/kvm/x86.c及mmu/mmu.c/tdp_mmu.c。范围为普通用户态RAM的写保护跟踪模型，未证明配套Firecracker所用内核/模式一致。

VMM应在希望记录的写入之前开启跟踪，例如启动时登记slot即开启，或为迁移在运行中启用；跟踪没有开启时发生的历史写入不能靠之后打开标志找回。首次全量快照提供基线，后续dirty epoch需正确收集/重置并保留前次捕获后的修改；不能简单“到pause才开始跟踪”然后只存新dirty来补旧基线。

接口示意为KVM_SET_USER_MEMORY_REGION，原slot/GPA起点/HVA/size保持有效一致，仅增加KVM_MEM_LOG_DIRTY_PAGES flags（示意省略错误处理与其他flags）。kvm_prepare_memory_region按模式分配/复用位图，kvm_arch_commit_memory_region调用kvm_mmu_slot_apply_flags。在无cpu dirty-log辅助等条件的分支，remove_write_access以4KiB层级处理；TDP MMU调用kvm_tdp_mmu_wrprot_slot，按slot的GFN范围遍历有效root/叶项，修改已有SPTE写权限。尚未建立的映射由后续建表路径遵循logging策略，不需要提前为全RAM实体化全部叶项。

页定位依memslot的base_gfn/npages（GFN=GPA>>12，4KiB例）和KVM管理的二阶段页表，不是按Guest变量名搜索，也不要求先知道哪个页将写。源码用SPTE描述KVM管理的项，Intel EPT下最终权限可抽象为R/W/X。启用后调用kvm_flush_remote_tlbs_memslot，避免旧可写缓存继续使用；真实锁/原子更新、跨vCPU同步由内核完成，不能只把W位裸写成0。

示例slot=2、GPA起点0x400000、长度16KiB，Guest写GPA0x402120，对应GFN0x402及slot内页号2。退出给出相关故障地址/访问类型，KVM结合slot flags、SPTE及内存后备等判断原因，处理可跟踪写；位图bit2置位，按路径恢复写条件/重试。不是所有EPT violation都能按dirty处理，MMIO或其他权限问题另行分流。支持PML等辅助时部分路径清dirty位并收集硬件日志，不能断言所有页首次写都必须VM-Exit。初始全脏模式也可延后逐页保护。
