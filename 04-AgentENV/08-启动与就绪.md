## 1. 三层“就绪”，逐层收紧

| 层 | 判断什么 | 通过说明 | 不通过说明 |
|---|---|---|---|
| 进程/API socket | Firecracker 在、控制面可连 | 能配 VM、能 pause | VMM 没起来或 socket 路径不对 |
| 网络 | 宿主能经 tap0/virtio-net 到达 Guest | 包路通 | netns、网卡、IP 或端口不对 |
| envd 应用层 | `GET /health` 返回非 4xx/5xx | 服务能应答 | envd 未起、鉴权失败或内部错误 |

这是三个观察点，不是严格的网络层栈。envd 探测依赖网络，但 Firecracker API Unix socket 和 Guest 网络是独立通道；已经运行的 Guest 可能在 API 出现故障时仍能提供服务。失败原因须排查，不能从一次失败唯一定位某层。

## 2. `start()` 的两个子步骤

```cpp
// 形状示意
FirecrackerSandbox::start()
    → start_nowait()   // 做启动准备，等 API socket，再配置/启动或加载 VM；不等 envd
    → wait_for_ready() // 等待 envd 健康检查
```

来自 `sandbox.rs` 的注释与实现：

| 步骤 | 做什么 | 返回时保证什么 |
|---|---|---|
| `start_nowait()` | 准备 tools 盘、校验启动配置，按 Fresh/Resume 分支启动 | 启动命令已发出，API socket 可用 |
| `wait_for_ready()` | 取 `envd_instance`，调 `wait_for_ready(timeout, poll)` | envd 健康检查通过，或返回错误 |

`start_nowait()` 的注释明确写着“只等 API socket 可用”。这也是为什么存在 `start_nowait` 这个公开接口：**想先做其他准备、晚点再等 envd** 的调用方可以分开用。

## 3. envd 客户端对象长什么样

```text
EnvdInstance {
    base_path: "http://{guest_ip}:{control_plane_port}",
    grpc_address: 同一个 base_path,
    access_token: 可选鉴权,
}
```

三点：

- 对象只是**客户端配置**，创建它不代表 Guest 内服务在跑。
- HTTP 客户端与 gRPC `ProcessClient` 共用同一个地址，只是两个门面。
- 客户端保存可选 access token，具体请求是否携带及是否验证要按接口核对；固定版 health_get 未添加 X-Access-Token，不能把健康检查通过视为受保护命令调用的鉴权通过。

## 4. 健康检查的实际行为（已核对固定版本）

- 请求：`GET {base_path}/health`。
- 判定：HTTP 请求成功且状态码**不是 4xx/5xx** → 返回 Ok；**不校验响应体**。不要写成“必须等于 200”，204 之类也算通过。
- 单次上限：`min(1 秒, 剩余总时长)`；请求错误或单次超时都继续重试。
- 重试等待：`min(poll_interval, 剩余总时长)`；整体期限耗尽返回超时错误。
- 成功后：`wait_for_ready` 还会尽力通知 ublk daemon（tools 盘、内存快照设备可以放行后台下载），失败不影响本次就绪返回。

## 5. 为什么“端口能连”不等于“就绪”

三种探测的强度完全不同：

| 探测方式 | 能证明 | 不能证明 |
|---|---|---|
| 进程存在 / 对象已创建 | 配置准备好了 | 服务在监听 |
| TCP 端口可连接 | 网络栈与监听套接字在工作 | 应用能正确处理请求 |
| `GET /health` 返回非 4xx/5xx | 应用层能应答 | 每个功能都可用 |

健康检查是**应用层**请求，所以它能发现“进程在、端口开、但服务卡住”的情况。

## 6. 通过之后仍可能失败

- 一次探测只反映那个时刻；之后服务可能退出、重启或变慢。
- `/health` 通过不代表用户应用就绪，也不代表所有后续初始化完成。
- 在 AgentENV 里，`wait_for_ready` 之后还有设备通知等副作用，属于“就绪后续动作”，不是健康检查本身。

## 7. 边界与未核对项

- 未核对：envd 启动的内部流程、健康检查之外的功能可用性、部署版本与基线的差异。
- `start_nowait` 内部如何等待 API socket（重试次数、超时）未逐行核对。
- 源码核对不是服务器实测。

## 归档补充：Fresh 冷启动的准备项

在固定提交 sandbox.rs::start_fresh / configure_microvm 中核对到的主线：

1. 准备 tools 盘的工作路径，创建/连接用户镜像的 OverlayBD/ublk 后端，准备额外磁盘。
2. 组织内核启动参数，包括缺省 init=/init、网络 IP 等；分配网络资源和 namespace。扩展钩子等按配置出现。
3. 在相应 namespace 中启动 Firecracker；在 server 内建立 envd 客户端对象。
4. 等待 Firecracker API 可用，配置内存/vCPU、内核镜像、磁盘、网卡等。
5. 发送 VM 启动动作；Guest 内核、初始用户空间和 envd 随后启动，start 的外层再等待 envd 健康探测。

此 Fresh 配置中 `/dev/vda` 是只读 tools/root 设备，`/dev/vdb` 是可写用户镜像；不要把普通教学中的“vda 就是用户 rootfs”当作这个版本的全部实际布局。Guest 后续挂载、切根和用户配置初始化还需沿 Guest 脚本核对。Resume 是另外的状态加载分支，不把 Fresh 步骤直接套到恢复。
