# 第 5 课：Firecracker 线程与暂停

关联：[学习计划](00-学习计划.md) · [第 4 课](04-Guest指令执行.md) · [学习记录](学习记录.md)

2026-10-24 开始。本页只保存当前教学入口；线程间具体消息、唤醒机制和暂停确认流程，留待核对所用 Firecracker 版本的源码。下图是职责示意，不是完整调用链。

## 当前介绍的分工

| 角色 | 主要工作 |
|---|---|
| API 线程 | 接收和解析外部控制请求 |
| VMM 线程 | 协调虚拟机状态和设备事件 |
| vCPU 线程 | 调用 KVM_RUN，推动 Guest 指令执行 |

```text
AgentENV server 请求暂停
    ↓
Firecracker API 接收请求
    ↓
VMM 协调暂停
    ↓
各 vCPU 配合退出 Guest 执行并进入暂停等待状态
```

“API 收到暂停请求”与“所有 vCPU 均已暂停”是不同的完成点。暂停 vCPU 不等于销毁虚拟机或保存完整快照。

## 2026-10-26：暂停与宿主侧写入

- 两个 vCPU 共享 Guest RAM。只暂停其中一个，另一个仍可执行 Guest 写指令。
- 宿主暂时没有调度某个 vCPU 线程，不等于它已确认暂停：再次获得时间片时，前者仍可能继续执行 Guest；后者需要遵守暂停等待状态，直到获准恢复。
- 发出暂停请求与收到全部 vCPU 的暂停确认是不同完成点。
- Firecracker 整个进程承担 VMM 角色；“VMM 线程”则特指其中协调状态、处理设备事件等工作的线程，不能把线程和整个进程混为一谈。

```text
Guest 写入：vCPU 执行 Guest 指令 → GVA → GPA → HPA
宿主设备代码写入：宿主线程执行代码 → Firecracker HVA → HPA
```

两条路径可以到达同一物理页。宿主软件设备写接收缓冲区，不需要 vCPU 执行 Guest 的写指令；Guest 驱动处理该数据则需要 vCPU 执行。实际暂停时设备是否继续处理，仍需核对所用版本，不能把上述能力当作已经观察到的暂停行为。

用户正确回答宿主侧设备写入不依赖 vCPU 执行，并询问 VMM 与 Firecracker 的关系；这是局部正确证据。“未获调度与已暂停”的区别已讲解，未独立复述。完整快照还需协调设备侧状态与可能的写入源。
