# 第 5 课：Firecracker 线程与暂停

关联：[学习计划](00-学习计划.md) · [第 4 课](04-Guest指令执行.md) · [第 6 课](06-VirtIO描述符队列与通知.md) · [学习记录](学习记录.md)。

本页整理 2026-10-24 起的对话，2026-11-02 按前四课的结构重写。线程划分参考 Firecracker 上游设计，**未逐函数核对 AgentENV 部署版本**；暂停确认的具体消息与唤醒机制留待后续。

## 1. 先分清进程与线程

| 对象 | 是什么 | 主要工作 |
|---|---|---|
| Firecracker | 一个宿主进程 | 承担 VMM 职责：内存、设备、vCPU、控制接口 |
| API 线程 | 进程内的线程 | 在 Unix socket 上接收并解析控制请求 |
| VMM 线程 | 进程内的线程 | 协调虚拟机状态、处理设备事件 |
| vCPU 线程 | 每个 vCPU 一个线程 | 调 `ioctl(vcpu_fd, KVM_RUN)`，推动 Guest 执行 |
| 设备处理逻辑 | 通常由 VMM 事件循环等执行上下文承载 | 处理 VirtIO 后端；不能默认每个设备都有独立线程 |

两个容易混的位置判断：

- **`FirecrackerInstance` 不是 Firecracker 进程**，它是 server 进程里的管理对象，保存 socket 路径和子进程句柄。
- **Guest 里的程序不是宿主普通子进程**。Guest 由 Guest 内核调度；宿主普通 `ps` 不会将 Guest Python 列成 Firecracker 的原生子进程，但专门的虚拟机观测工具可以另行分析。

## 2. 线程分工为何有用

一个单线程的 VMM 会卡在下面这个矛盾里：

```text
Guest 正在执行
    → 承载它的 vCPU 线程处于 ioctl(KVM_RUN) 调用中，未在执行 Firecracker 用户态代码
    → 如果进程只有一个线程，此时无法同时处理“请暂停”的控制请求
```

拆开之后：

- vCPU 线程负责“Guest 在跑”的时间；
- API 线程负责“随时能接请求”；
- VMM 线程负责把请求翻译成对 vCPU 与设备的协调动作。

“线程处于 KVM_RUN 调用中”不等于“线程睡眠或没有占用 CPU”：物理 CPU 可能正在这个线程的执行上下文中运行 Guest。只有 Guest halt、等待事件等情况，线程才可能被阻塞。其他 VMM 设计可以采用不同组织方式，这里解释 Firecracker 的分工，不宣称多线程是所有虚拟机的唯一方案。

## 3. 暂停请求到达后发生什么

以两个 vCPU、控制面收到暂停请求为例（时刻与编号均为课堂假设）：

```text
t0  vCPU0、vCPU1 都在 KVM_RUN 中，Guest 在执行
t1  API 线程收到 PATCH /vm，state = Paused
t2  VMM 线程开始协调：置暂停意图，请求各 vCPU 退出
t3  vCPU0 遇到退出条件，从 KVM_RUN 返回，进入暂停等待
t4  vCPU1 此刻没有被宿主调度 —— 它并没有“确认暂停”，只是没在跑
t5  vCPU1 被调度，收到退出要求，处理后进入等待
t6  两个 vCPU 都确认，暂停完成，API 返回响应
```

`t4` 是这一课的核心：**“没有获得调度”是调度状态，“已暂停”是协议状态**。前者随时可能被重新调度并继续执行 Guest；后者要等恢复指令才继续。

## 4. 三个完成点

| 完成点 | 含义 | 不能推出什么 |
|---|---|---|
| 请求已发出 | 本地把字节写进了 socket | 对方收到、开始处理 |
| Firecracker 已接收 | API 线程解析成功 | 所有 vCPU 已停下 |
| 全部 vCPU 确认暂停 | 没有任何 vCPU 还能执行 Guest 指令 | 快照已保存 |

为什么需要确认：停止 vCPU 是捕获一致状态的必要协调步骤。如果只把状态标成 Paused，而某个 vCPU 还在写 Guest RAM，后续读到或保存的内容就可能不一致。设备侧是否静止还需单独协调，不能由 vCPU 确认推导全部状态冻结。上面 t0—t6 是职责推演，不是已逐函数确认的消息时序。

## 5. 暂停 vCPU 不等于整台机器停住

两个 vCPU 共享同一块 Guest RAM。只暂停其中一个时：

- 另一个 vCPU 仍可执行 Guest 写指令，内存继续变化；
- 设备侧可能仍有宿主线程在处理请求（是否继续取决于实现，未核对）。

因此“暂停一个 vCPU”只能叫“部分停下”，不能叫“VM 已暂停”。

## 6. 两条写内存的路径

```text
Guest 执行写：vCPU → GVA →（Guest 页表）→ GPA →（EPT）→ HPA
宿主设备写：  宿主线程 → Firecracker 的 HVA →（宿主页表）→ HPA
```

两条路径可以落到同一块物理页，因为 Guest RAM 被 Firecracker 映射进自己的地址空间。由此得到本课最实用的结论：

- **宿主软件设备往 Guest 接收缓冲区写数据，不需要 vCPU 执行 Guest 指令**；
- **但 Guest 驱动要处理这批数据，仍然需要 vCPU 运行**。

前者是“宿主线程执行代码写共享内存”，后者是“Guest 代码在读内存”，两个动作的主体不同。

## 7. 暂停、销毁、快照是三件事

| 动作 | 执行状态 | 内存与进程 | 结果 |
|---|---|---|---|
| 暂停 | 停止执行 Guest | 都还在 | 可恢复运行 |
| 销毁 | 停止该实例 | 清理相关运行时资源，共享资源按拥有关系回收 | 具体完成条件需检查清理结果 |
| 快照 | 通常基于暂停 | 需捕获状态并写出 | 可持久化、可恢复 |

暂停成功只保证“现在不跑了”，快照还要读内存、写文件，可能失败；失败后是否回滚、是否保持暂停，按实现核对。

## 8. 答题证据与待验证项

- 用户正确判断：宿主设备写 Guest RAM 不需要 vCPU 执行（本课局部正确证据）。
- 用户正确判断：两个 vCPU 不等于永久独占两个物理核；VM-Exit 不必然切换宿主线程。
- 已讲解但未独立复述：“未获调度”与“已暂停”的区别。
- 未核对：线程间消息与唤醒机制、暂停确认协议、暂停时设备线程是否继续处理。
- 课程保持学习中；讲解与材料生成不计独立验收。
