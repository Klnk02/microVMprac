# 第 2 课：一个指针属于谁

关联：[学习计划](00-学习计划.md) · [第一课](01-系统地图与第一课.md) · [学习记录](学习记录.md) · [第 3 课](03-Guest内存与宿主映射.md)

本课解决：为什么 server 不能把 Firecracker 的一个虚拟地址直接交给普通 `pwrite` 使用。先只讨论两个宿主进程，不引入 Guest 页表和 EPT。

## 1. 先复述第一课的位置

server 与 Firecracker 是两个不同的宿主进程，均由宿主内核管理。Guest 中的 Python 由 Guest 内核管理；server 保存的 Firecracker 子进程 PID 不能直接当作 Guest Python 的 PID。

这是教师给出的解释，不表示用户已通过第一课验收。

## 2. 地址数值相同，数据可以不同

下面是假设的映射，仅用于纸面推演，不能用于真实程序直接解引用。两个进程都可以有虚拟地址 `0x400000`：

| 地址空间 | 虚拟地址 | 对应宿主物理页 | 页面中的示意内容 |
|---|---|---|---|
| server | `0x400000` | P_A | `SERVER` |
| Firecracker | `0x400000` | P_B | `GUEST-DATA` |

虚拟地址这个数字需要结合所属进程的地址空间才有含义。在这个例子中，两边页表分别把同一数字映射到不同物理页。

另一个可能情况是 server 根本没有映射这个地址。不能因为它在 Firecracker 中有效，就认定在 server 中同样有效。

## 3. 普通 pwrite 没有远程进程参数

接口形状是：

```cpp
ssize_t pwrite(int fd, const void* buf, size_t count, off_t offset);
```

- `fd`：调用进程的文件描述符，决定写哪个已打开文件。
- `buf`：当前调用进程的源缓冲区地址。
- `count`：尝试写多少字节。
- `offset`：目标文件的写入位置。

如果 server 调用下面的伪代码：

```cpp
pwrite(snapshot_fd, (void*)0x400000, 4096, file_offset);
```

内核按 server 地址空间解释 `0x400000`。在前面的课堂假设中，它读取 P_A 中的 `SERVER` 所在页面；它不会自动判断调用者想要 Firecracker 中 P_B 的内容。

若换成 Firecracker 发起相同形状的调用，`buf` 就按 Firecracker 的地址空间解释。这说明限制来自调用参数所描述的数据源，不是宿主内核做不到地址翻译。

## 4. process_vm_readv 把远程来源说清楚

Linux 原生接口形状如下，本课只看参数角色：

```cpp
ssize_t process_vm_readv(
    pid_t pid,
    const iovec* local_iov, unsigned long liovcnt,
    const iovec* remote_iov, unsigned long riovcnt,
    unsigned long flags
);
```

它额外描述了远程进程 PID，以及本地和远程两组内存范围。`iovec` 可以先理解为“地址 + 长度”的一条描述；此时不需要了解所有高级用法。

在 AgentENV 的 pause 提取路径里：

| 对象 | 本课中的实际含义 |
|---|---|
| 调用者 | AgentENV server |
| `pid` | 要读取的 Firecracker 宿主 PID |
| `local_iov` 描述的区域 | server 中用于接收内容的缓冲区 |
| `remote_iov` 描述的区域 | Firecracker 地址空间内映射的 Guest RAM 范围 |

回到纸面例子，另外假设 server 有目的缓冲区 `0x900000`：

```text
process_vm_readv：
  源 = Firecracker PID + 其地址 0x400000
  目的 = 当前 server 的地址 0x900000

完成后：server 的目的缓冲区获得了 GUEST-DATA
```

普通 `pwrite(snapshot_fd, server_buffer, ...)` 随后才能读取 server 中这份数据。`process_vm_readv` 完成并不表示已经写了文件。

## 5. 对应当前代码

固定版本 [ProcessVmReader](https://github.com/kvcache-ai/AgentENV/blob/9f62cbe07cebfecf416dc9bdcf497e2a97687644/src/sandbox/firecracker/process_vm_reader.rs) 在 `read_exact_remote` 内：

- 用 `remote_addr` 与长度构造一个 `RemoteIoVec`。
- 用目的切片 `remaining` 构造一个 `IoSliceMut`。
- 将保存在 reader 里的目标 `pid`、本地范围和远程范围传给 `process_vm_readv`。
- 返回字节不足时继续处理剩余范围；失败时返回错误。

这几步把“到哪个进程找源地址、写到自己的哪里”明确交给内核。方法名中的 offset 在这个具体 reader 中表示 Firecracker HVA，而不是普通文件偏移；以后看到同名 trait 参数，先检查具体实现的含义。

## 6. 三个动作分开画

```text
① 描述地址：创建 local/remote iovec 元数据
   数据仍在源页面，创建描述本身不复制 payload

② 跨进程读取：process_vm_readv
   Firecracker 的源页 → server 的目的缓冲区

③ 写文件：pwrite 或所选 writer 的文件写入操作
   server 的缓冲区 → 目标文件的相应写入路径
```

由内核执行一次复制，不表示必然先复制到另一个中间内核 buffer，再复制到目的地。这里按接口可确认的源、目的和完成点理解，内部实现另课追踪。

## 7. 本课只检查一题

课堂假设不变：server 的 `0x400000` 对应 P_A，Firecracker 的 `0x400000` 对应 P_B。现在由 **server** 调用普通 `pwrite`，`buf` 参数填 `0x400000`。

**它会读取 P_A 还是 P_B？如果希望写 P_B 的内容，现有 AgentENV 路径先做了哪个动作？**

后续迁移题：若 Firecracker 自己调用 `pwrite`，为什么源地址的解释会变化？这个变化是否自动让原始内存文件变成有效 OverlayBD 层？后半题在存储与快照课再解，不要求现在跳到格式实现。
