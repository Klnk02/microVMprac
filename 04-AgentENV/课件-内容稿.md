## P01 封面：30 分钟把 AgentENV 讲成一条链

**一句话**：三个执行环境、六条链路、一个「完成点」判断，构成本讲全部内容。

**知识点**

1. **三个执行环境不是"三层软件栈"，是三种执行主体。**
   宿主用户态有三个独立进程：AgentENV server（生命周期、快照、控制面）、Firecracker（VMM：vCPU 线程 + 设备模型）、ublk-daemon（集中式块设备服务）。宿主内核里是功能而非进程：KVM（`/dev/kvm` + ioctl）、ublk 驱动（`/dev/ublkbN` 请求队列）、cgroup/seccomp（约束）。Guest 里是另一套完整内核与进程表。判断标准只有一条：**这个对象有没有自己的 PID、由谁的内核调度**。

2. **六条链路是"验收单位"，不是章节顺序。**
   创建 / 执行 / 读文件 / 暂停 / 恢复 / 销毁。每条链都有 3—4 个完成点，且完成点分属不同层。例：读文件链的四个完成点是 FETCH 的 CQE 到、daemon 提交 COMMIT、设备发布 used、`read()` 返回——把任意一个当成"全完成"都会误判。

3. **全篇只有一个判断句：这一步的"完成"由谁判定、下一层知道了吗。**
   具体展开：`ioctl(KVM_RUN)` 返回 ≠ Guest 执行完（可能只是 KVM 处理完退出又重入）；设备发布 `used` ≠ Guest 驱动已处理（还差中断注入与调度）；`finalize` 成功 ≠ 已持久化（还差 fsync）。

4. **三个可交付能力。**
   能画出位置图（谁在哪层）、能说出每层完成点、能用四段式（结论→机制→边界→证据）讲任一机制 ≥90 秒。没有第三条，前两条只算"看过"。

5. **证据规矩。**
   数字必须带口径（单位、范围、版本）；没实测的写"量级"或"资料不足"。本讲所有性能数字（冷/热恢复延迟、PVM 耗时、MMIO 退出开销）**均为未实测**，不写具体毫秒。

**易错点**：把「28 课都讲过」当成「会讲」——学习记录里独立验收是 0/28。
**自测**：不看讲义，说出三个执行环境里各有哪些进程，以及哪些对象没有 PID。
**如果只记一件事**：所有答案都落在「谁在哪一层、这一步算完成了吗」。
**版式**：封面｜**模拟图**：迷你知识地图｜**数据图**：三个数字卡（3 环境 / 6 链路 / 27 页，常量）

## P02 知识地图：依赖顺序是位置→地址→执行→存储→状态→平台

**一句话**：跳过前两个模块，后面每个模块都会以"名词记忆"收场。

**知识点**

1. **六个模块的依赖不是并列，而是三层。**
   地基：位置（谁在哪层）、地址（GVA/GPA/HVA/HPA）。中间：执行（KVM_RUN/VM-Exit 语义）、存储（virtio → ublk → 层）。上层：状态（快照/恢复）、平台（资源/并发/度量）。依赖是硬的：不懂退出语义，就分不清"发布 used"和"Guest 已处理"。

2. **一个具体的依赖例子。**
   `process_vm_readv(pid, local_iov, riovcnt, remote_iov, riovcnt, flags)` 的四个参数：`pid` 选地址空间、`local_iov` 是调用者缓冲、`remote_iov` 里放的是**Firecracker 的 HVA**、`liovcnt/riovcnt` 是**元素个数不是字节数**、`flags` 必须为 0。不懂四条地址线，这四个参数只能死记。

3. **三个「易混区」及其成因。**
   状态：暂停、快照、恢复本是三件事，却有"停顿"这一共同表象。平台：资源拥有（谁创建）与引用消失（谁还在用）是两回事。存储：逻辑偏移、层内偏移、后端位置三个坐标系。

4. **本讲回答的 5 个问题（3 高频 2 理解）。**
   ① Guest 里的进程在谁那边、宿主 `ps` 能看到吗 ② 一次 4 KiB 读，到哪一步算完成 ③ 暂停能否说明快照成功 ④ namespace/cgroup/seccomp 各挡什么 ⑤ 恢复后旧 TCP 为何可能不通。

5. **为什么"易混区"恰好是面试高频区。**
   因为它们都涉及"完成点"与"作用对象"两个容易被跳过的维度；答题者往往直接说结论（"快照成功""隔离了"），而面试官追的是"哪一步、哪一层"。

**易错点**：跳过地址直接看快照，会把「按需缺页」「COW」「持久化」当成同一件事。
**自测**：「恢复后首条命令慢」必须先懂哪个机制，为什么？
**如果只记一件事**：先建结构（谁在哪层），再记细节（那层的完成点）。
**版式**：总结｜**模拟图**：依赖 DAG｜**数据图**：各模块前置依赖数条形（计算值）

## P03 三个执行环境：只有 Guest 有自己的内核

**一句话**：进程、线程、内核功能三种对象混在一起，是所有位置题答错的总根源。

**知识点**

1. **Firecracker 是宿主进程，有直接实现证据。**
   `instance.rs` 里 `Command::new(&firecracker_binary)` 只准备参数；`spawn_tokio_command_scoped(...)` 返回 `child` 才是真正启动；随后 `self.process = Some(child)` 保存句柄，`child.id()` 拿到的是**宿主 PID**。这三步要分开：准备 → 启动 → 保存句柄；`Command::new` 前后系统里什么都没多。

2. **内核功能没有 PID，不能画成进程框。**
   KVM 是 `/dev/kvm` 上的 ioctl 集合，ublk 驱动是块设备子系统，cgroup/seccomp 是内核机制。它们不出现在 `ps` 里；把 KVM 画成"一个进程"会让"谁在执行 Guest 指令"这个问题永远讲不清。

3. **Guest 里的程序由 Guest 内核调度，宿主看不到。**
   它存在于 Guest RAM 的一段字节里，靠 Guest 页表 + EPT 翻译访问；宿主 `ps` 只看到 firecracker 的若干线程。**推论**：宿主 PID 与 Guest PID 是两套编号空间，不能互相代入。

4. **两条跨层通道，载体完全不同。**
   控制面：宿主 Unix socket（`--api-sock`），Firecracker REST，如 `PATCH /vm {state: Paused}`、`PUT /snapshot/load`。应用面：TCP，经 tap0 + netns DNAT 到 Guest 的 envd（HTTP `/health` 与 gRPC `ProcessClient` 共用同一 base 地址，带 access token）。前者不需要 Guest 配合，后者需要。

5. **`FirecrackerInstance` 是管理对象，不是进程。**
   它存在 server 的地址空间里，保存 socket 路径与 `Child` 句柄；`pause()` 是这个对象经 socket 发请求。函数名不意味着调用者进入了 Guest。

**易错点**：把 `FirecrackerInstance` 当进程；把宿主 PID 当 Guest PID；把 KVM 画成进程。
**自测**：宿主执行 `ps -eLf`，能列出哪几个？列不出来的对象凭什么说它们"在"？
**如果只记一件事**：先问「这个对象有没有自己的 PID、由谁的内核调度」。
**版式**：概念｜**模拟图**：三层带 + 两条通道｜**数据图**：进程/线程计数条形（常量+计算）

## P04 四把尺子：GVA/GPA/HVA/HPA 各属于谁

**一句话**：同一块物理页有两条访问路径，HVA 只属于其中一条。

**知识点**

1. **两条翻译链，各自用各自的表。**
   Guest 访存：`GVA →（Guest 页表）→ GPA →（EPT）→ HPA`。Firecracker 访存：`HVA →（宿主页表）→ HPA`。两条链落在同一物理页，所以**不存在"两份内存要同步"**；存在的是"两份页表指向同一页"。

2. **登记接口的实际字段，解释了为什么没有 HPA。**
   `KVM_SET_USER_MEMORY_REGION{ slot, flags, guest_phys_addr, memory_size, userspace_addr }`。用户态拿不到物理地址，只能交 HVA 起点；是宿主内核查宿主页表把 HVA 翻成 HPA，再去填 EPT。**所以参数里没有 HPA 字段，不是省略，而是不可能。**

3. **偏移公式与代入。**
   `HVA = userspace_addr + (目标 GPA − guest_phys_addr)`。例：`0x70000000 + (0x2000 − 0) = 0x70002000`。该值直接作为 PVM 的 remote 地址；`remote_iov` 里的地址是**Firecracker 的 HVA**，不是 GVA，也不是 GPA。

4. **memslot 有两个硬约束。**
   一是数量上限：Firecracker 用 `kvm.max_nr_memslots()` 校验，超了报 `NotEnoughMemorySlots`——碎片化登记会先撞这个上限。二是每条 memslot 可带 dirty log：快照的"哪些页要存"就是按位图拿的，粒度是 memslot 的 GFN 范围。

5. **EPT 按需建立，登记不等于占内存。**
   登记只记录范围关系；访问到缺项时 KVM 才按 memslot 算出 HVA、取真实页（可能触发缺页）、再建 EPT 项。所以登记 128 MiB 不会立刻占 128 MiB，而且缺项退出**通常由 KVM 内核处理完直接重入**，不必返回用户态。

**易错点**：以为 Guest 正常访存会经过 HVA；以为 memslot 就是 EPT 表；以为登记时复制了一份 RAM。
**自测**：`guest_phys_addr=0`、`userspace_addr=0x70000000`，访问 `GPA 0x2000` 时 PVM 的 remote 填什么？为什么不是 GPA？
**如果只记一件事**：地址是名字，进程是语境。
**版式**：概念 + 公式｜**模拟图**：双路径汇合｜**数据图**：翻译次数对比（Guest 2 次 / FC 1 次，常量）

## P05 三个切换：只有线程切换才是真没拿到 CPU

**一句话**：把三种边界混成一个，就没法把"慢"拆开。

**知识点**

1. **KVM_RUN 是系统调用：进内核、换特权级、线程不变。**
   它返回时携带一个退出原因（`kvm_run->exit_reason`），如 `KVM_EXIT_MMIO`、`KVM_EXIT_IO`、`KVM_EXIT_HLT`。注意命名层次：硬件层面的退出原因是 `EXIT_REASON_EPT_VIOLATION`，KVM 对用户态暴露的是 `KVM_EXIT_MMIO`——**同一个事件在两层的名字不同**。

2. **VM-Exit 是硬件行为，硬件负责存/取现场。**
   撞到 VMCS 配置的退出条件时，CPU 把 Guest 的寄存器等写入 VMCS 的 guest-state area，把退出原因与 exit qualification 写入 VM-exit information 字段，再从 host-state area 载入宿主状态切到根模式。**这一步不需要软件主动发起**，软件只是事后读原因。

3. **KVM 能处理的退出，处理完直接重入。**
   典型：普通 RAM 的 EPT 缺项——KVM 按 memslot 取页、建项、重入 Guest，`ioctl` 从头到尾没返回过用户态。只有它办不了的（MMIO/PIO 需要设备模型模拟），才把控制权交回 Firecracker。

4. **三个指标必须分开报。**
   退出次数（硬件，看 `exit_mmio_*` 这类计数）、被唤醒次数（用户态）、上下文切换次数（调度器）。它们互为因果但不可相加；把三者混成"虚拟化开销"，就无法定位是设备模型重、CPU 被抢、还是 IO 等待。

5. **"慢"的三分类给排障用。**
   退出太多 → 看设备模型与 MMIO 频率；线程被抢 → 看超订与 cgroup 配额；IO 等待 → 看缺页与后端延迟。分类之前先采集这三类计数，不要凭感觉。

**易错点**：把 VM-Exit 当 KVM_RUN 返回；把"补 EPT 映射"的开销算到设备模型头上。
**自测**：一次 EPT 缺页退出会让 FC 从 `ioctl` 返回吗？判据是什么？
**如果只记一件事**：看到"慢"先分三类——退出 / 调度 / IO。
**版式**：对比｜**模拟图**：状态迁移（用户态/内核/Guest）｜**数据图**：是否切线程矩阵（定性）

## P06 vCPU 与线程：一个 vCPU 就是一个宿主线程

**一句话**：多线程不是为了更快，而是为了让宿主在任何时候都能下指令。

**知识点**

1. **线程创建的实际代码路径。**
   `lib.rs:397` 对每个 vCPU 调 `start_threaded(vcpu_seccomp_filter.clone(), barrier.clone())`；`vcpu.rs:246` 里 `thread::Builder::new().name(format!("fc_vcpu {index}")).spawn(闭包)`。闭包内三件事按顺序：`init_thread_local_data()` → `barrier.wait()` → `self.run(filter)`。

2. **`Barrier::new(vcpu_count + 1)` 的 +1 是主线程。**
   `lib.rs:372` 建 barrier，`lib.rs:401` 主线程也 `wait()`。语义：所有 vCPU 线程完成 TLS 初始化后，主线程才继续去发"启动虚拟机"。若去掉 barrier，先跑起来的线程可能进入 `run()`，而其他 vCPU 还没准备好，Guest 一开机就可能撞到未初始化状态。

3. **线程名是代码写死的，不是自动继承。**
   `.name("fc_vcpu {i}")` 决定 `ps -eLf` 里看到的名字；内核 `comm` 字段上限 16 字节（含 `\0`），所以名字最长 15 字符。不写 `name()` 就只有默认名，排障时会认错线程。

4. **"在 KVM_RUN 里"≠"线程空闲"。**
   物理 CPU 可能正在该线程上下文中执行 Guest 指令，所以 CPU 占用率包含"跑 Guest"的时间；只有 Guest 执行 `HLT`、等中断这类情况，线程才真正被阻塞。用 CPU 占用率判断 VMM 忙不忙会误判。

5. **代价：线程数决定三件资源的粒度。**
   seccomp filter 每线程一份（见 P19）、cgroup 记账按 task 粒度、调度与缓存亲和按线程走。配 N 个 vCPU 就是 `1+1+N` 个线程，密度场景下这个数字直接乘上沙箱数。

**易错点**：以为 vCPU 线程闲置；以为线程名会自动从变量名来。
**自测**：配 2 个 vCPU 的 VM，宿主至少几个线程？`Barrier` 为什么是 `vcpu_count + 1`？
**如果只记一件事**：线程数 = 1（vmm）+ 1（api）+ N（vcpu）。
**版式**：概念｜**模拟图**：进程框 + 线程 + barrier 同步点｜**数据图**：线程数随 vCPU 数变化（计算：1+1+N）

## P07 控制面与数据面：两条通道，两种故障

**一句话**：控制面不依赖 Guest，数据面依赖 Guest——这决定了"Guest 卡住时还能不能停"。

**知识点**

1. **控制面的载体与典型调用。**
   宿主 Unix socket（`--api-sock`），消息是 Firecracker REST：`PATCH /vm {state: Paused}`、`PUT /snapshot/load`（带 `mem_backend`、`resume_vm`、`network_overrides`）、`GET /vm/dirty-memory-ranges`。这些请求由 Firecracker 自己的 API 线程解析，**不需要 Guest 调度**。

2. **数据面的载体与依赖。**
   Guest RAM 里的 virtqueue：描述符表 + avail 环 + used 环 + 门铃。设备与驱动必须协作推进，**Guest 内核卡死时队列不再前进**。这是数据面的本质局限，不是实现缺陷。

3. **为什么暂停不能走数据面。**
   暂停的用途之一正是"Guest 不配合时也能停住它"。若停机依赖 Guest 处理队列，就变成"要停下它得先让它运行"的循环论证。

4. **超时的三种可能，不能互相代入。**
   ① 请求没送到（连接断、FC 未监听）② 做成了但响应丢了（VM 其实已暂停）③ 还在做（vCPU 未调度、IO 卡住）。因此超时既不能推出"VM 还在跑"，也不能推出"操作失败"；重试要幂等。

5. **故障表现对照。**
   控制面坏：不能暂停/快照/销毁，但 Guest 照常运行。数据面坏：Guest 内部 IO 卡住，但宿主仍能控制与捕获。排障时先问"哪一面坏了"，能省一半时间。

**易错点**：把 socket 当网络；把超时当失败；以为"HTTP 所以要走网络栈"。
**自测**：超时后补发一次 `resume` 会有什么风险？举一个具体坏结果。
**如果只记一件事**：socket 是宿主之间，virtqueue 是 Guest 参与。
**版式**：对比｜**模拟图**：双通道 + 故障点｜**数据图**：Guest 正常/卡死 × 两通道可用性（定性矩阵）

## P08 VirtIO：队列在内存里，通知只提醒

**一句话**：设备不是"收到包"，而是"去共享队列取一条描述"；这是它比模拟设备快的根本原因。

**知识点**

1. **split virtqueue 的三个结构。**
   描述符表：每项 16 字节（`addr` 64 位 = 缓冲区 GPA、`len` 32 位、`flags` 16 位含 `NEXT`/`WRITE`、`next` 16 位）。avail 环：Guest 发布链头编号（设备可用的缓冲）。used 环：设备发布完成项与实际写入长度。三者在 Guest RAM 里，设备访问前必须做 GPA→HVA 换算与范围校验。

2. **通知（doorbell）的语义边界。**
   它只表示"去检查队列"：不携带包内容、不保证一项对应一次通知、可以被抑制（批量处理）。一次通知可对应多项工作——例：avail 有链头 3、7、9，只敲一次门铃。所以**通知次数 ≠ 请求数**。

3. **缓冲区的生命周期与复用风险。**
   同一链头发布两次＝两次使用机会，不是同一个包发两次。Guest 未处理完 `used` 里的数据就把缓冲再发布，设备可能覆盖仍需读取的内容——这是"看起来偶发"的数据错乱来源。

4. **为什么批量能省。**
   模拟真实设备时，每个寄存器访问都是一次 VM-Exit；VirtIO 把数据放共享内存里批量搬，只在"有活"时敲一次门铃，把 N 次退出压成 1 次。注意节省的是**退出与模拟**，不是"数据本身不经过内存"。

5. **内存顺序与实现边界。**
   真实驱动需要内存屏障保证 avail/used 的可见顺序，还可能有通知抑制（`EVENT_IDX`）等优化。本讲只讲交接语义，不把这些简化成"发个信号就行"；不同设备/内核版本的具体行为需按实现核对。

**易错点**：把"设备发布 used"当"Guest 已处理"；把通知次数当请求数。
**自测**：Guest 未处理完就把缓冲区再次发布，会发生什么？为什么这种 bug 难复现？
**如果只记一件事**：队列在内存、通知只提醒、数据在 buffer。

## P09 三层就绪：一层比一层强

**一句话**：进程在、端口通、应用能应答，是三件强度不同的事。

**知识点**

1. **第一层：API socket 可用。**
   能配 VM、能 pause。它证明 VMM 起来了、`--api-sock` 路径对；此时 VM 可能还没配置、更没启动。`start_nowait()` 就停在这一层——注释写明"只等 API socket 可用"。

2. **第二层：网络可达。**
   宿主经 tap0 能到 Guest；证明 netns、网卡、IP、端口都对。这一层的失败常被误诊为"服务没起来"。

3. **第三层：`/health` 通过。**
   `GET {base}/health`，判定是**状态码非 4xx/5xx**（不校验 body，204 也算过）；单次上限 1 秒（`HEALTH_PROBE_TIMEOUT`），失败继续重试，整体期限耗尽才报超时；`wait_for_ready()` 在这一层。

4. **health 不带 token，别把它当鉴权。**
   envd 客户端把 `base_path` 与 `grpc_address` 设为同一地址，`access_token` 单独保存并用于受保护请求；health 请求未带 token。所以"health 通过"只说明应用能应答。

5. **排障顺序：先 socket、再网络、最后应用层。**
   跳层排查会把"网络不通"误诊成"服务没起来"，把"鉴权失败"误诊成"服务挂了"。每层都有独立观测手段：socket 用 `nc -U`，网络用 `ping/curl`，应用层用 `/health` 与日志。

**易错点**：把 health 通过当完整可用；把它当鉴权通过；把"对象创建成功"当"服务就绪"。
**自测**：端口能连、命令返回 `UNAUTHENTICATED`，问题在哪层？health 为什么排除不了它？
**如果只记一件事**：就绪答三层，比"服务起来了"多拿一分。
**版式**：流程｜**模拟图**：阶梯 + 时间轴｜**数据图**：重试次数随总期限（计算：期限/poll，单次上限 1s）

## P10 exec 事件流：返回的是流，不是结果

**一句话**：`Start` 只证明进程被创建，成功要三样同时满足。

**知识点**

1. **接口形状。**
   `start_process_inner(cmd, args, envs, cwd)` 打包成 `StartRequest`，经 envd 的 gRPC `ProcessClient.start` 发送，返回的是**流**，调用方必须持续消费到结束。

2. **三类事件的准确含义。**
   `Start{pid}`：进程已创建（pid 是 Guest 内 PID）。`Data`：stdout/stderr 分段，可能 0 条也可能很多条，两个通道都可能写。`End{exit_code}`：进程已退出。注意"收到 Data"既不证明成功也不证明失败。

3. **两个独立判断。**
   ① 事件是否收齐（收到 End = Ok；流断了 = Err，属协议层）。② `exit_code` 是否 0（属程序层）。`wait` 返回 Ok 只代表"取得了结果"，不代表程序成功。

4. **成功三件套。**
   `wait` 返回 Ok + 收到 End + `exit_code` 符合预期。只有 `Start` 时，之后仍可能脚本报错、崩溃、权限/路径问题、被超时杀掉。

5. **没有 shell，与超时的两处坑。**
   命令与参数分开传，不假设经 shell 解析：没有管道、通配符、重定向；需要时显式 `sh -c`。超时后发终止请求可能失败，所以不能断言进程已退出；结果未知时重试可能重复执行，业务侧要幂等。

**易错点**：看到 Start 就当成功；只看 exit_code 不看流是否收齐；把"超时"当"已退出"。
**自测**：可执行文件根本起不来时，一定会先收到 `Start` 吗？这个答案如何影响你的判错逻辑？
**如果只记一件事**：Start 之后追两件事——End 到了吗、退出码是多少。
**版式**：流程｜**模拟图**：事件时间轴 + 两判断｜**数据图**：事件类型 × 含义表

## P11 六层读路径 + 三个偏移：每层的"完成"都不一样

**一句话**：排障就是把"卡在哪一层、哪个完成点"定位出来。

**知识点**

1. **六步链。**
   `read()` → ext4 把文件偏移换成 LBA（extent 映射）→ virtio 描述符链 + 门铃（MMIO → VM-Exit）→ ublk 请求入队（queue id + tag）→ daemon 查 OverlayBD 定层取字节 → 原路返回填 Guest 页缓存。

2. **四个完成点。**
   ① `UBLK_IO_FETCH_REQ` 的 CQE 到 = 请求**送到** daemon；② daemon 提交 `COMMIT` = 它交差；③ 设备发布 `used` = 设备侧交差；④ `read()` 返回 = 应用拿到字节。四者不能互相代入。

3. **三个坐标系与 8 倍单位差。**
   文件偏移（字节）、LBA（块号）、后端位置（层内偏移/远端）。同一 8 MiB：按 512 B 扇区编号是 16384，按 4 KiB 块编号是 2048。**报 LBA 不带单位等于没报。**

4. **缓存改变的不只是速度。**
   Guest 页缓存命中可免掉这批数据的设备 IO；但路径解析、元数据、并发预读仍可能产生 IO。所以"缓存命中"不能推出"整次调用零设备请求"。

5. **写路径四节点。**
   `write` 进 Guest 页缓存 → 脏页回写交 virtio → 后端写层文件 → `fsync/flush` 才算持久化。`write` 返回只代表进了页缓存；`O_DIRECT` 绕过页缓存但改变了对齐与时序要求。

**易错点**：把 FETCH 的 CQE 当"数据读完"；把"缓存命中"当"零 IO"；报偏移不带单位。
**自测**：FETCH 的 CQE 到了但后端读失败，哪些层还能报成功？`read()` 会返回什么？
**如果只记一件事**：问"完成了吗"必须先说清是哪一层。
**版式**：流程｜**模拟图**：六步 + 四完成点｜**数据图**：512 B vs 4 KiB 编号对比（计算，8 倍）

## P12 分层覆盖：无记录要回落，显式零要终止

**一句话**：叠加是"同一逻辑位置的替换关系"，不是"把层文件拼起来"。

**知识点**

1. **索引与读取规则。**
   每层一张索引：逻辑区间 → 本层内位置（`tag` + `moffset`）。读取时从最新层往下查，第一个有记录的就赢，命中即停；都没命中则是空洞（按只读镜像语义返回零）。

2. **四情形要能手算。**
   父层 A/B/C/无，上层 无/X/显式零/无：位置0 → A（回落）；位置1 → X（覆盖，父层 B 仍在但被遮住）；位置2 → 全零（显式零遮蔽父层 C）；位置3 → 零（空洞）。四种结果有两种都是 0，但语义不同。

3. **"无记录"与"显式零"的语义差别。**
   无记录 = 这层没管这段，要继续往下找；显式零 = 我明确写过这里全是 0，必须在此终止。把后者当前者，会读回父层旧数据——不报错，属静默损坏。

4. **单位与校验。**
   基础对齐 512 B（`lsmt/file/types.rs` 的 `ALIGNMENT`），页与逻辑块常用 4 KiB；写入 OverlayBD 时按 512 换算。转换函数会校验：`page_size` 必须是 4096、`image_offset + length` 不得溢出完整镜像大小、排序后拒绝目的范围重叠。

5. **两处实现边界。**
   一个逻辑读可能跨多段层内数据（逻辑连续 ≠ 层内连续）；后端读失败必须作为错误返回，不能静默当空洞——否则是数据损坏而不是零。

**易错点**：把"显式零"当"无记录"；把"后端读失败"当零返回；以为一个逻辑读只对应一段层内数据。
**自测**：父层有旧值、新状态应为全零，能省略这条覆盖记录吗？不加会读到什么？
**如果只记一件事**：拼接字节只能得到 A/B/C/D/X/Y，表达不了"X 替换位置 1"。
**版式**：对比（2×2）｜**模拟图**：三层索引 + 四情形｜**数据图**：四情形查层数条形（计算：1/1/2/3 层）

## P13 ublk 与 daemon：内核给壳，用户态给内容

**一句话**：内核只负责"第几块、多长"，格式与远端都在用户态。

**知识点**

1. **三个设备节点各管一段。**
   `/dev/ublk-control`：全局管理（创建/删除/设参数）。`/dev/ublkcN`：该设备的命令交接通道，daemon 从这里拿请求描述。`/dev/ublkbN`：对外读写的块设备，Firecracker `add_drive` 挂的是它。

2. **创建流程与一个易漏的竞态。**
   server 发 `CreateOverlaybd{image_config, global_config}` → daemon 向 ublk 驱动注册设备 → 内核分配 N → daemon **等节点"真正可打开"**（不只是文件存在：udev 可能还没改好组与权限，非 root 消费者会打开失败）→ 回 `(dev_id, device_path)`。

3. **四步处理，第一步最容易误解。**
   ① 等待：在 io_uring 上提交"有活给我"。② 领取：CQE 带回 queue/tag/偏移/长度，**只表示请求送到**。③ 解析：OverlayBD 查索引，定层、定偏移、取字节（命中缓存可能不碰盘）。④ 提交：`COMMIT_AND_FETCH_REQ` 可合并"报告完成 + 挂下次等待"，但**不表示下一项已处理完**。

4. **集中式的收益与代价。**
   收益：设备创建成本低、缓存集中、不用每沙箱 fork 服务。代价：单点——daemon 无响应则该节点全部块 IO 停滞或失败；快照恢复前 `sandbox.rs` 会检查 ublk client 可用。

5. **错误语义与设备编号。**
   后端读失败必须沿链返回，daemon 不能当零；设备编号由内核分配，不能当固定 ID，server 保存的是 `(dev_id, device_path)`。另有 `pack_recording` 分支走 `create_dedicated_mem_device`（每沙箱一份），那条路径的共享行为未逐一核对。

**易错点**：把 FETCH 的 CQE 当数据读完；把 daemon 当内核模块或每沙箱一个进程；把设备号当固定 ID。
**自测**：Firecracker 挂盘用哪个节点、daemon 收请求用哪个？两者为什么不能混？
**如果只记一件事**：内核搬"第几块、多长"，其余全在用户态。
**版式**：流程｜**模拟图**：三节点 + 四步｜**数据图**：三种角色 × 三节点映射表（定性；队列深度资料不足不画）

## P14 mmap / 缺页 / COW：写才复制

**一句话**：映射是登记，分配在缺页，复制在首次写。

**知识点**

1. **mmap 只建 VMA。**
   `mmap(NULL, 128 MiB, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)` 成功只建立虚拟范围与属性；不预填充时不会立刻分配 128 MiB 物理页。`prot` 决定"能不能"，不决定"有没有页"。

2. **缺页三类，处理路径不同。**
   minor：页已在内存（零页、page cache），映射即可。major：页不在，要读文件或换入，产生真实 IO。非法访问：无有效映射或权限不符 → SIGSEGV（文件映射也可能 SIGBUS）。**写保护缺页不属于非法访问**，那是 COW 的正常处理。

3. **两种写语义。**
   `MAP_SHARED`：写进共享缓存并按同步/回写规则写回文件。`MAP_PRIVATE`：写只影响自己的私有副本，不回写文件。fork 后父子共享物理页、PTE 都设只读，任一方写才复制——**COW 不在 fork 时发生**。

4. **microVM 里同时有三层缺页。**
   Guest 页表（Guest 内核处理，宿主不知情）、EPT（KVM 处理，常能补完直接重入）、宿主页表（匿名页分配或文件页读入）。所以"恢复后很慢"要指出是哪一层缺页，不能笼统说"缺页"。

5. **已核验的映射模型。**
   Firecracker `1.12.1` 的 `vstate/memory.rs:136` 用 `libc::MAP_PRIVATE` 映射快照内存后端；AgentENV 侧同一模板沙箱共享同一只读 ublk 设备与页缓存（`src/sandbox/ublk/device.rs:573-582`）。合起来：**读共享页缓存、写才 COW 出私有页**。

**易错点**：以为 mmap 就占内存；以为 COW 在 fork/mmap 时发生；把三层缺页混成一个"缺页率"。
**自测**：恢复后"第一次读一页"和"第一次写一页"分别发生什么？哪一步会碰后端存储？
**如果只记一件事**：RSS 不涨不代表没映射，只是还没被访问。
**版式**：流程｜**模拟图**：三态 + 三层缺页｜**数据图**：RSS 随访问页数增长（示意，标未实测）

## P15 快照四件套：缺一件就恢复不出同款机器

**一句话**：状态、内存、磁盘、配置各有独立完成点，pause 只是第一件。

**知识点**

1. **四件套逐项。**
   VM 状态（vCPU 寄存器、指令位置、设备状态）→ 决定"从哪继续执行"；内存镜像（RAM 字节，可增量+父层）→ 决定"变量是什么值"；磁盘视图（rootfs 层 + 额外盘 + 父层引用）→ 决定"文件长什么样"；恢复配置与索引（层顺序、设备关联、兼容参数）→ 决定"怎么拼回去"。

2. **捕获主线（已核对的调用）。**
   `pause_to_dir` →（有可写持久卷时先经 envd 同步其文件系统）→ `fc_instance.pause()` → `snapshot_to_dir` → `create_state_only_snapshot(type=Diff)` + `get_dirty_memory_ranges()`（`GET /vm/dirty-memory-ranges`）→ `convert_dirty_memory_to_overlaybd(FC PID, 范围, ...)` → 组合父层 + 写 manifest。

3. **四个完成点。**
   暂停（vCPU 全确认）→ 捕获（读内存/写层/出状态文件）→ 持久化（fsync/上传）→ 释放运行时（关实例、回收资源）。每一段都可能失败，且失败后留下的残留不同。

4. **一致性的具体反例。**
   真实顺序 x=100→90、y=100→110；采集到 x=100 与 y=110，就拼出"从未同时存在"的状态。暂停能挡住 Guest CPU 写入，但宿主设备侧仍可能写同一块 RAM——所以完整方案还要协调设备与在途 IO。

5. **三处容易越界的边界。**
   ① 文件系统同步 ≠ 用户程序私有缓冲已 flush ≠ 外部数据库事务已提交。② `finalize` 只保证格式完成，`rename` 只切换名字，都不等于断电持久化。③ VM 内部一致 ≠ 业务一致：外部支付/对账不会随快照回滚。

**易错点**：pause 成功就当快照成功；单个 `vm_state.bin` 写成功就当整套可用；把 fsync 当业务事务提交。
**自测**：哪一步失败会造成"快照文件存在但恢复不了"？说出两个候选点。
**如果只记一件事**：四件套 + 四完成点，缺一不可。
**版式**：概念｜**模拟图**：四格 + 四完成点时间轴｜**数据图**：四件套结构条（体积未实测，只标件数）

## P16 暂停三完成点：没被调度不是已暂停

**一句话**：调度状态是随机的，协议状态是确定的；快照只能要后者。

**知识点**

1. **时间线 t1—t6。**
   t1 API 线程收到 `PATCH /vm` → t2 VMM 线程置暂停意图、请求各 vCPU 退出 → t3 vCPU0 从 `KVM_RUN` 返回并确认 → t4 vCPU1 **没被调度**（≠ 暂停）→ t5 vCPU1 被调度后才处理退出要求 → t6 两个都确认，暂停完成。

2. **三完成点。**
   请求已发出（本地写进 socket）/ Firecracker 已接收（API 线程解析成功）/ 全部 vCPU 确认（没有 vCPU 还能执行 Guest）。三者各自检查，不能互相代替。

3. **为什么必须等确认。**
   只把状态标成 Paused 而某个 vCPU 还在写 Guest RAM，后续读到或保存的内容就可能不一致。这跟"暂停一个 vCPU 不算 VM 暂停"是同一条道理的两种说法。

4. **暂停的边界。**
   它只停 Guest 的 CPU 写入；宿主设备侧仍可能在写同一块 RAM；设备 drain 与在途 IO 要单独协调。因此"全部 vCPU 确认"是必要条件，不是"所有写入源静止"的充分条件。

5. **暂停之后的四步仍会失败。**
   捕获内存、写层、fsync/上传、改 manifest；任一步失败都可能留下半成品（源码里有临时文件清理与上层恢复逻辑，详细异常路径需按实现核对）。

**易错点**：把"请求发出"或"API 返回成功"当"VM 已停"；把暂停完成当"快照已保存"。
**自测**：只暂停两个 vCPU 里的一个，能叫"VM 已暂停"吗？为什么？
**如果只记一件事**：暂停 ≠ 快照；确认 ≠ 持久化。
**版式**：流程｜**模拟图**：t1—t6 时间线｜**数据图**：完成点 × 等待对象表（常量；暂停耗时为未实测，不画）

## P17 恢复路径：不是把内存读回来

**一句话**：只读后端 + 按需缺页 + 写时 COW；恢复成功只代表"能开始跑"。

**知识点**

1. **五步链。**
   检查 ublk 可用 → 备盘/备网 → `load_snapshot_file(..., BackendType::File, mem_backend_path=/dev/ublkbN, resume_vm=false, ...)` → 补新挂载卷/MMDS/限流 → `fc_instance.resume()`。

2. **`resume_vm=false` 的理由。**
   先把状态、设备关联、网络、额外盘都装好，最后才让 vCPU 执行；否则 Guest 会在配置不全时开始跑，表现为"随机的初始化失败"。

3. **一页怎么变可访问。**
   Guest 访问 GPA → 宿主页表缺项 → 向只读内存设备发块读 → daemon 查 OverlayBD 取这一块 → 填进宿主页 → Guest 继续。写这一页则 COW 到私有层，共享镜像不动。

4. **共享与私有（已核验）。**
   同一模板的沙箱共享同一个只读 ublk 设备，因而共享同一页缓存（`device.rs:573-582` 注释原文）；Firecracker 以 `MAP_PRIVATE` 映射（`memory.rs:136`），写时才 COW。所以"多实例不会各占一份 4 GiB"成立，但也不是"全都不占"。

5. **三样不随快照恢复的东西。**
   外部对端状态（TCP 可能已超时/关闭）、宿主 conntrack/NAT 映射、超时与租约计时器。另有克隆体需要重随机化的项：PID、RNG 种子、时钟、序列号、主机名/IP。所以恢复后应按"重连"设计。

**易错点**：以为恢复会预读全部内存；以为恢复 VM 就恢复了业务状态；用"旧连接续用"做默认假设。
**自测**：恢复后首条命令慢、内存指标却不高，是故障还是正常？用什么指标证明是缺页？
**如果只记一件事**：恢复 = 重建机器 + 装载状态，不是"重新开机"。
**版式**：流程｜**模拟图**：五步 + 一页缺页｜**数据图**：两段完成（load 返回 / 首命令）示意，冷热延迟未实测

## P18 网络两方向：出站 SNAT，入站 DNAT

**一句话**：两条方向相反的路，同名接口靠 netns 隔开。

**知识点**

1. **出站链路。**
   Guest eth0 → VirtIO-net → TAP fd → 沙箱 netns 的 tap0 → 路由 → **SNAT（源改成 slot 的 host_interaction_ip）** → vpeer/veth pair → 主 netns → **MASQUERADE（源改成出口地址）** → 出口。两层 NAT 各解决一件事：区分实例、适配出口。

2. **入站链路。**
   server 连 `host_interaction_ip:port` → veth 进沙箱 netns → PREROUTING **DNAT（目的改成 Guest vm_ip）** → tap0 → Firecracker → VirtIO RX → Guest TCP/IP → envd。

3. **同名 tap0 为何不冲突。**
   每个 netns 有独立的接口命名空间；先由 netns 隔开，再用 slot 专属地址区分实例。这也解释了"200 个沙箱各有 tap0"为何合法。

4. **返回包靠状态，不靠"读包再转发"。**
   conntrack 记录 NAT 映射并逆向还原，配合 `ESTABLISHED/RELATED` 放行。恢复快照不会把 conntrack 一起带回，所以"Guest 里 socket 还在却连不通"是常见现象。

5. **策略分支与它的边界。**
   TCP 80/443 可被 REDIRECT 到出口代理（看 HTTP Host 或 TLS ClientHello 的 SNI）；基线声明不终止 TLS、不改写 HTTP。它只覆盖 TCP，不是通用域名防火墙；已有连接的策略效果与新连接不同（改 deny 不一定断已建立的转发）。

**易错点**：TX 的 `used` 只表示缓冲可回收，不代表远端收到；把 TCP 重定向当全协议白名单。
**自测**：两个沙箱的 Guest 用同一段 IP，为什么不冲突？改策略会断旧连接吗？
**如果只记一件事**：网络不通先分方向——出站看 SNAT/路由，入站看 DNAT/端口。
**版式**：对比｜**模拟图**：上下两条链｜**数据图**：veth/规则数随沙箱数增长（计算+示意）

## P19 四道门与 seccomp：先定威胁，再选控制点

**一句话**：seccomp 约束的是 VMM 发出的宿主 syscall，不是 Guest 里的 syscall。

**知识点**

1. **四类威胁对应四个边界。**
   A Guest 内作恶（没越门，Guest 内核用 `pid_max`/`RLIMIT_NPROC` 限制）、B VMM 被攻破（已越虚拟化边界，靠 seccomp/降权/chroot/caps/LSM）、C 资源超用（cgroup 限值/vCPU/balloon）、D 网络外连（netns/iptables/代理）。

2. **seccomp 的装载位置与线程级语义。**
   `vcpu.rs:276 run()` 第一件事就是 `apply_filter`，失败 `panic!`；filter 以 `Arc<BpfProgram>` 传入，每个 vCPU `clone()` 后各自安装（`lib.rs:369/397`）。**线程级**：同进程不同线程可有不同白名单。

3. **白名单规模与失败动作。**
   Firecracker `1.12.1` 默认三组 `vmm 60 / api 35 / vcpu 43` 条，`default_action = trap`；命中未允许 syscall → **SIGSYS 直接杀进程**（不是 EPERM）。`BPF_MAX_LEN = 4096`，超长直接报错。

4. **安装的前置条件。**
   `seccomp.rs:99` 先 `prctl(PR_SET_NO_NEW_PRIVS, 1)`，再 `syscall(SYS_seccomp, SECCOMP_SET_MODE_FILTER, 0, &prog)`。顺序颠倒且无 `CAP_SYS_ADMIN` 会 EACCES；这也是"非特权进程能给自己上锁"的前提。

5. **两条常被问穿的边界。**
   ① Guest 内部 syscall 由 Guest 内核处理，seccomp 完全看不到。② `pids.max` 只数宿主 cgroup 里的 task，挡不住 Guest 内 fork bomb；宿主侧兜底是 `memory.max`（OOM 杀整台 VM）、`cpu.max`、vCPU 数。

**易错点**：以为 seccomp 能约束 Guest；以为 namespace 里的 root 已无特权；把"升级 FC 崩了"当偶发（其实是新 syscall 不在白名单）。
**自测**：Guest root 执行任意 syscall 会被 seccomp 拦吗？那 Guest 内 fork bomb 靠什么限制？
**如果只记一件事**：namespace 改视野、cgroup 改用量、seccomp 改能力，不可替代。
**版式**：对比｜**模拟图**：2×2 威胁×门 + 线程级装配｜**数据图**：三组白名单条数 60/35/43（常量）

## P20 HVA 公式：登记不复制

**一句话**：算出的是 Firecracker 的 HVA，不是 GVA、不是 HPA。

**知识点**

1. **公式与变量。**
   `HVA = userspace_addr + (目标 GPA − guest_phys_addr)`。`userspace_addr` 是登记时给的 HVA 起点；`guest_phys_addr` 是这段 GPA 的起点；目标必须落在**同一条 memslot** 内。

2. **代入一个数。**
   登记 GPA 起点 0、HVA 起点 `0x70000000`、长度 128 MiB；访问 `GPA 0x2000` → `0x70000000 + 0x2000 = 0x70002000`。这个值直接作为 `process_vm_readv` 的 remote 地址。

3. **跨 memslot 就会算错。**
   若有两条：GPA `0..64 MiB`→HVA `0x70000000`，GPA `64 MiB..128 MiB`→HVA `0x80000000`，访问 `GPA 0x4010000` 必须先在第二条里算：`0x80000000 + 0x10000`。用第一条公式会得到错误地址，且 PVM 可能仍"成功"读到别的页。

4. **公式给的是软件关系。**
   EPT 项是否已建立要另看：访问缺项时 KVM 才按 memslot 取页建项；页面未驻留时还可能触发缺页。公式不保证"这一页已经在内存里"。

5. **常见变形与用途。**
   反算 `GPA = guest_phys_addr + (HVA − userspace_addr)`，用于把宿主侧看到的地址折回 Guest 逻辑位置；调试时用它验证"这段字节到底属于哪一页"。

**易错点**：把 HVA 当 GVA 传给 Guest；跨 memslot 直接套公式；以为算出地址就能读（还要考虑驻留与权限）。
**自测**：两条 memslot 如第 3 条所述，访问 `GPA 0x4010000` 时 HVA 是多少？
**如果只记一件事**：公式只在"同一条 memslot 内"成立。
**版式**：公式｜**模拟图**：地址线段 + 目标页｜**数据图**：三组 GPA→HVA 换算表（计算）

## P21 例题1：这题考「完成点」

**一句话**：CQE 的语义由它对应的命令决定，不由"它到了"决定。

**知识点**

1. **题面与已知。**
   daemon 收到 `UBLK_IO_FETCH_REQ` 的 CQE（带回 queue/tag/偏移/长度）；后端是只读层 + OverlayBD。问：能否断言"这个 4 KiB 已从盘上读到"。

2. **步骤1：先定位命令语义。**
   这条 CQE 对应"领取请求"命令，只说明**请求已交付**给 daemon；它不含数据，也不代表后端读过盘。

3. **步骤2：列出还差的动作。**
   查 OverlayBD 索引 → 定层 → 取字节（命中缓存可能不碰盘）→ 填 daemon buffer → 提交 `COMMIT`。注意"填 buffer"发生在 daemon 侧，不在 Guest 侧。

4. **步骤3：给判据。**
   `COMMIT` 完成、内核完成原块请求后，数据才算到宿主侧；`pread` 返回 4096 时字节在 daemon buffer 里，还要经 Firecracker 写进 Guest 页，最后 `used` 发布、`read()` 返回。

5. **迁移：后端读失败会怎样。**
   `COMMIT` 应带错误返回，内核完成原块请求为失败，Firecracker 不应发布"成功的 used"；Guest 侧应看到 IO 错误而不是 4 KiB 数据。若实现把失败当零返回，就是静默损坏。

**易错点**：把"领取完成"当"IO 完成"；把 FETCH 的完成与普通 READ 的完成混为一谈（两者 CQE 的 `user_data` 含义不同）。
**自测**：缓存命中时，这条链上有哪几步可以完全跳过？
**如果只记一件事**：凡是 CQE/回调/事件，先问它对应哪条命令。
**版式**：例题｜**模拟图**：四完成点阶梯｜**数据图**：四步「是否已取字节」矩阵（常量）

## P22 例题2：这题考「作用对象」

**一句话**：机制作用在谁身上，决定了它能不能回答这道题。

**知识点**

1. **题面与已知。**
   seccomp 白名单装在 firecracker 的线程上（`vmm 60 / api 35 / vcpu 43`）；Guest 有独立内核。问：Guest 里的 root 执行任意 syscall 会被拦吗。

2. **步骤1：syscall 由谁处理。**
   Guest 内 syscall 进入 **Guest 内核**，由 Guest 内核的服务例程处理；它根本没有发出宿主 syscall，宿主 seccomp 无从拦截。

3. **步骤2：seccomp 拦的是谁。**
   它拦的是 firecracker 自己发出的宿主 syscall（`open`/`mmap`/`ioctl`…），防的是"VMM 被攻破之后"的破坏力：提权、加载模块、开新设备。

4. **步骤3：那 Guest 内 fork bomb 靠什么。**
   Guest 内核的 `pid_max`、`RLIMIT_NPROC`；宿主侧兜底是 `memory.max`（OOM 杀整台 VM）、`cpu.max`、vCPU 数。**`pids.max` 无效**：它只数宿主 cgroup 里的 task。

5. **迁移：如果 Guest 内核自身有提权漏洞。**
   seccomp 挡不住——那是虚拟化边界内的 Guest 内问题，要靠 Guest 内核补丁、最小化 Guest 攻击面；宿主侧只剩硬件虚拟化边界这一层。

**易错点**：把 seccomp 当"给 Guest 用的沙箱"；把 namespace 里的 root 当已无特权。
**自测**：谁能拦住 Guest 里的 fork bomb？写出两个控制点，并各说一个它管不到的维度。
**如果只记一件事**：每题先问"这个机制作用在哪个对象上"。
**版式**：例题｜**模拟图**：syscall 路径（Guest 内核 vs 宿主 seccomp）｜**数据图**：三方交叉表（Guest 进程 / FC 线程 / 宿主 task × 谁限制它）

## P23 六个高频错答：错在哪一句

**一句话**：这些错答的共同病根是把"某层完成"当"整件事完成"。

**知识点**

1. **`pids.max` 能挡 Guest 内 fork bomb。**
   错在对象：`pids` 控制器数的是宿主 cgroup 里的 task；Guest 进程只是 Guest 内存里的数据结构。正确兜底：`memory.max`（OOM 杀整台 VM）、`cpu.max`、vCPU 数、balloon。

2. **`VM-Exit` 就等于 `KVM_RUN` 返回用户态。**
   错在边界：KVM 能处理的退出（补 EPT 映射）处理完直接重入，`ioctl` 从未返回。正确的是"退出原因在硬件层，是否回用户态看 KVM 能否处理"。

3. **namespace 隔离等于降权。**
   错在语义：namespace 只改"看见什么"，ns 里的 root 仍是 root。要降权得 uid/gid 切换 + drop capabilities（必要时 userns）。

4. **`finalize + rename` 等于已持久化。**
   错在完成点：`finalize` 保证格式处理完成，`rename` 只切换名字；断电安全要 `fsync`，完整快照还要 manifest 与父层引用一起发布。

5. **health 通过等于鉴权通过 / 只读块设备等于各实例各自匿名页。**
   前者错在请求内容（`/health` 不带 token）；后者错在映射模型——同一模板共享同一只读 ublk 设备与页缓存（`device.rs:573-582`），Firecracker 用 `MAP_PRIVATE`（`memory.rs:136`），写才 COW。

**易错点**：六条错答都能"听起来很顺"，因为都省略了"哪一层/哪一步"。
**自测**：用自己的话重讲第 1、2、5 条，各加一个数字或 file:line。
**如果只记一件事**：看到"等于/挡住/不影响"这类绝对化说法，先问它管的是哪一层。
**版式**：易错｜**模拟图**：红绿对照 6 行｜**数据图**：错误类型计数（计算：把层完成当整体 3 条 / 把视野当权限 2 条 / 其他 1 条）

## P24 记忆卡：5 个数字 + 一条主线

**一句话**：面试里数字比形容词可信，但数字必须带口径。

5. **`3` / `4`**：暂停三个完成点（发出/接收/全部确认）；快照四个完成点（暂停/捕获/持久化/释放）。

**易错点**：数字不给口径；把上游默认值当部署值。
**自测**：这 5 个数字分别落在哪一层？哪个最容易被追问"你的版本是多少"？
**如果只记一件事**：如果只记三件事——三个执行环境、每层完成点、暂停≠快照≠恢复。
