# 第 24 课 / A5：性能指标怎样读

2026-11-13 按面试重点提前进入，其他课次状态保留。本轮先讲 wall time、CPU time 和等待/排队，采用纸面示例，无实际测量。

## 1. 先确定测量对象

以 Guest pread 请求到返回为端到端区间。Guest 的用户读取完成、Firecracker 后端读取完成、ublk daemon 后端 READ 完成属于不同边界。一次请求的延迟与整个进程在时间窗内累计的 CPU 不能直接相减解释等待。

## 2. 三个概念

- wall time 是起止时刻的实际经过时间，包含运行、等待、排队和调度延迟；测量持续时间通常选单调时钟。
- CPU time 是指定线程/进程实际占用 CPU 的累计时间，可区分 user/system；多线程并行累计可以超过 wall time。
- off-CPU 是选定线程没有在 CPU 上执行的时间，原因包括阻塞等待和可运行但未获调度。请求还可能由其他线程/内核工作处理，off-CPU 不自动等于物理磁盘时间。

仅对同一线程、同一时间窗，可把 wall 减该线程 CPU 近似理解为未在 CPU 执行的时间。迁移到跨进程异步链路需要按对象分别观测。

## 3. 假设的 10 ms 请求

| 时间段 | 关键路径工作 |
|---|---|
| 0—1 ms | Guest 发布块请求 |
| 1—2 ms | Firecracker 接收并提交后端 IO |
| 2—3 ms | ublk 交付与 daemon 索引处理 |
| 3—8 ms | 后端读取的等待区间（需进一步拆排队/设备服务等） |
| 8—9 ms | 数据交付、ublk/VirtIO 完成 |
| 9—10 ms | Guest 处理结果、复制给用户并返回 |

总延迟 10 ms。表中各段为假设的互不重叠关键路径区间，不是测得的 CPU 时间，也不适用于直接相加嵌套 span。某步骤函数 wall 变长可能来自锁、调度、缺页、存储等，需进一步证据。

若仅优化 1 ms 的处理，使其降为 0.5 ms，且其他阶段不变、无额外成本、无并发影响，则请求降为 9.5 ms，延迟减少 5%。局部耗时减半不代表端到端减半。

## 4. 诊断步骤

先固定起止边界、请求大小/并发、镜像与缓存状态，再保存重复样本。分开观测 vCPU、Firecracker 后端、daemon 线程的 CPU 与等待，追踪同一请求在各层的时间点。可用时钟需可比较；Guest 与 Host 时间戳不可未经校准直接相减。涉及预取、异步内核工作、并行或后台流量时单列统计边界。

复习题：单个 daemon IO 线程在 10 ms 区间消耗 CPU 1 ms，能否断定磁盘读取用了另外 9 ms？两个线程各运行 8 ms 且并行、wall 为 10 ms，总 CPU 16 ms 是否矛盾？10 ms 请求中仅 1 ms 阶段减半，端到端延迟变为多少？

来源：[clock_gettime 的单调时钟、进程/线程 CPU 时钟](https://man7.org/linux/man-pages/man3/clock_gettime.3.html)。请求时间线与优化数字均为教学假设。

## 5. 延迟、CPU 计量与 perf

2026-11-13 用户问实际统计方法。本轮仅提供工具用法，未执行性能测试。

- 单次延迟：操作前后取 CLOCK_MONOTONIC 的差；异步操作从提交前测到对应请求真正完成。请求间用稳定身份关联，跨 Guest/Host 时间戳需要校准。
- 延迟分布：保存每次结果，固定并发和缓存条件后报告样本数、p50/p95/p99、失败与超时。大量请求下并行使批次 wall 除以请求数不能替代请求延迟分布；很少样本的 p99 不稳定。
- CPU：用 CLOCK_THREAD_CPUTIME_ID 或 CLOCK_PROCESS_CPUTIME_ID 取区间差；getrusage 可分 ru_utime 与 ru_stime。线程等待让出 CPU 时不计该线程 CPU，忙轮询计入。进程计量包括自身线程，不自动包括独立 daemon 和子进程；并发服务的进程 CPU 差包含其他请求。
- perf stat 统计选定对象的计数，如 task-clock/context-switches/page-faults，适合相同工作量、环境和窗口下对比。perf stat -- ./bench 仅按选定目标范围统计，不自动涵盖已运行的独立 daemon。
- perf record 对指定事件采样，perf report 查看热点。示例 cpu-clock 采样用于 CPU 路径，采样占比不等于整个请求 wall 占比，热点百分比不直接表示可卸载收益。采样权限、栈展开、符号与额外开销影响结果。

沙箱/DSA 实验建议分别记录端到端延迟、server/Firecracker/daemon/独立 worker CPU，并标明重复/遗漏计量风险。线程或进程总 CPU 用于成本，CPU 采样用于解释热点，等待需额外时间线或调度/IO 事件。先保持工作量、缓存、并发及测量对象一致。

工具来源：[perf stat](https://man7.org/linux/man-pages/man1/perf-stat.1.html)、[perf record](https://man7.org/linux/man-pages/man1/perf-record.1.html)、[getrusage](https://man7.org/linux/man-pages/man2/getrusage.2.html)。

## 6. 从 /proc 读取 CPU 记账

用户提到 stime 和 ctime。/proc/PID/stat 中常用的是第 14 字段 utime、第 15 字段 stime；第 16/17 字段 cutime/cstime 是已等待回收的子进程 CPU 记账，没有名为 ctime 的对应 CPU 字段。不要默认子进程字段包含所有仍在运行的子进程。

两次采样的进程 CPU 秒数为 Δ(utime+stime)/sysconf(_SC_CLK_TCK)。tick 换算值可用 getconf CLK_TCK 查询，不硬编码 100。例如 CLK_TCK=100，两次总计数相差30，则 CPU 增长0.30秒。用 CPU增量/wall增量×100% 得到单逻辑CPU=100%的利用率，多线程可超过100%。短阶段受对外导出粒度与采样开销影响，应结合高分辨率CPU时钟/批量工作观测。

单线程使用 /proc/PID/task/TID/stat。解析须处理括号内 comm 可能含空格等情况，避免盲目按空白切分定位字段；跨采样检查 starttime 以防 PID 复用。Firecracker 的 utime 包含 guest_time，如已计入 utime，不应再重复相加 guest_time。

来源：[proc_pid_stat](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)。本轮仅解释接口与假设数字，无实际采样。

## 7. 联合解读总量、热点与请求延迟

教学假设：固定一批成功请求与环境，A/B 各100次，总完成时间10秒/10.5秒，选定全部组件总CPU为2秒/1秒，单请求p50为80ms/85ms，p99为200ms/300ms。可判断此批请求CPU成本由20降为10 CPU-ms/成功请求，但请求延迟及尾部变差；批次wall/N为100ms/105ms不能在有并发时当作请求平均延迟。CPU指标需相同范围/工作量并考虑失败与后台工作。

perf report 的百分比依事件与视图解释。本例显式选cpu-clock、自耗时Self视图，若 memcpy 占CPU样本40%，不能说请求wall的40%在复制，不能无条件按总CPU×40%当作精确函数计时。Children是含被调用函数的累计归因，与Self区别；嵌套调用链百分比不可逐行相加。

若想定位p99变差，需逐请求身份与阶段跨度，区别排队等待、锁等待、调度延迟、后端IO、轮询策略；CPU采样本身不能完整解释off-CPU等待。A/B比较固定请求数/大小、并发、缓存、统计范围，保存重复样本及原始数据。

课末题：CPU时间减半是否足以断言请求更快？cpu-clock样本中memcpy占40%能否推出10ms请求有4ms复制？并发100个请求在1秒内完成，是否能说每个请求延迟10ms？本节数字均为纸面教学，未运行perf。

## 8. 并发、吞吐与排队

并发数表示当前同时未完成的请求数量，既可能在运行，也可能等待。完成吞吐量为窗口内完成请求数/窗口长度，成功吞吐量需要另计成功数。并发不是线程数，异步线程可以管理多笔在途IO。

教学情形：一个可重叠IO等待的服务，逐级增加固定在途并发。假设并发1/4/16/64时，稳态成功吞吐约100/333/400/400请求每秒，平均延迟10/12/40/160ms。数字仅示意，并非测试结果；近似满足在途数≈完成速率×平均响应时间的稳态关系。

低并发时增加在途请求，可以利用空闲资源并重叠等待。达到瓶颈容量后，额外请求更多在排队，吞吐可能平台化，延迟继续增长，过载还可能让吞吐下降。瓶颈可能是CPU、锁、设备队列、内存带宽、限额或下游，不应仅凭吞吐平台就判断CPU满载。

如果稳定到达600请求每秒、系统最多完成400请求每秒，且无拒绝/取消/扩容等变化，队列约每秒增加200个请求；继续超时重试可能扩大负载。固定并发压测在请求变慢时自动降低发送速率，不等同固定到达率压测。成功/失败/超时分开报告，快速拒绝不能混进成功请求延迟美化结果。

复习题：并发16→64，吞吐400→400而平均延迟40→160ms，新增并发主要去了哪里？CPU利用率低但延迟高能否排除瓶颈？成功吞吐提高但超时也大增，是否足以断言方案更好？

来源：[AWS 关于过载、争用、延迟与有效处理能力的工程分析](https://aws.amazon.com/builders-library/using-load-shedding-to-avoid-overload/)。本节无真实压测。

## 9. 公平比较两个方案

用户在并发专题明确指出同一到达率下串行积压可能更多，已解释有效并发提升容量与饱和后继续加压是两种比较。用户把收益归因为等待重叠，已补充多核可并行计算，不以有阻塞作为必要条件。此处讲实验控制，无新实测。

先定义问题与工作量，例如固定大小60 MiB、并发1，对比CPU复制/DSA的端到端延迟与相同组件总CPU；再单独改变并发，不把单请求与高负载结果直接当作实现差异。CPU成本用同一窗口、同一覆盖范围下的累计CPU/成功工作量，并同时报告失败、超时和未完成任务。

缓存至少区分Guest文件缓存、Host后端数据缓存与CPU硬件缓存。A冷B热会混入缓存收益，应将冷热作为不同实验条件并明确定义。重复读取也可能包含后台预取与延迟初始化，不能只凭第二次更快就断言具体缓存层。

A/B比较时固定数据、镜像/快照链、并发、CPU/NUMA绑定和资源限额等相关条件，保存版本和原始结果；用多轮交替或随机顺序减少时间趋势影响，避免A全在冷机、B全在热机。采样数量按稳定性和尾部分布决定，少量样本不宜宣称p99改善。

记录端到端延迟、CPU、各阶段时点及错误；只优化搬运时，分别检查提交/等待/完成开销。示例A=10ms/1CPU-ms，B=9ms/1.4CPU-ms，表示延迟下降10%、CPU成本增加40%；方案选择由延迟/容量/成本目标决定，不压成无条件“更快更好”。

复习题：A在冷缓存、并发1测，B在热缓存、并发8测，B吞吐更高能否归因于实现？B延迟降低但CPU/请求增加，应补充什么目标决定取舍？本节不建议在共享机器上直接清理全局缓存或操作公司服务。

## 11. 完成已经发生，线程为何还未处理

阻塞等待的线程在事件发生后变为可运行，实际继续执行还受调度影响。分开设备实际完成、完成记录可见/等待者被唤醒、线程开始处理、对外返回等时点；各机制的通知路径与开销不同，不假定一次唤醒对应一个请求。

教学假设：DSA在100us完成，忙轮询线程在102us看到完成并于105us返回；阻塞线程在103us变为可运行、120us获调度、123us返回。例子说明后者CPU可能更省、延迟反而较高；这些数字无实测依据。轮询自身也会被抢占或受带宽/争用限制，不保证总是更快。

混合策略可先轮询一段预算时间，再通过正确的内核等待/通知协议阻塞。检查完成状态与进入等待之间的竞态必须由等待机制正确处理，不能简单“检查一次然后睡眠”以免漏通知。并发较高时，轮询还可能抢占真正生产数据、提交完成的线程，增加整体延迟。选择策略依据CPU/延迟实测和资源预算。
