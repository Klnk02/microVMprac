# 第 18 课：从快照恢复

2026-11-05。基线 `9f62cbe07cebfecf416dc9bdcf497e2a97687644`。关联：[第 17 课](17-chunk写出与快照封存.md) · [学习记录](学习记录.md)。本课核对 sandbox.rs 的 resume、resume_from_snapshot_config、start、start_resume、acquire_shared_mem_device，以及 instance.rs 的 load_snapshot_file；映射与 COW 机制依据同版本架构文档，未重新审计配套 Firecracker 的底层 mmap 实现，未做真实 VM 实验。

## 1. 先分清两种恢复

- 原地恢复：运行时仍在，FirecrackerSandbox::resume 直接调用 fc_instance.resume，不必重新读快照重建 RAM。
- 从快照恢复：resume_from_snapshot_config 创建 sandbox 对象并调用 start；按保存的 VM 状态、内存镜像、磁盘及配置重新准备运行环境。本课讲普通恢复路径，不展开 pack_recording 分支。

新运行环境可以采用预启动的 Firecracker 和网络槽位；不等于每次一定新 spawn，也不等于旧 Guest 仍在原进程中等着继续。

## 2. 对象位置与用途

| 对象 | 所在位置与作用 |
|---|---|
| AgentENV server | Host 进程；准备资源、取得设备句柄、调用 Firecracker API |
| VM 状态文件 | 保存寄存器、设备等状态；与 RAM 内容配套 |
| 内存 OverlayBD 层与配置 | 组合为完整的逻辑 RAM 镜像；包含父层回落关系 |
| 内存 ublk 设备 | Host 只读块设备，向 Firecracker 提供 RAM 镜像；不是给 Guest 新增的磁盘 |
| Firecracker | Host 进程；加载 VM 状态、映射内存后端、借 KVM 运行 Guest |
| Guest 磁盘后端 | 为 Guest 文件系统提供虚拟磁盘；与 RAM 镜像是不同用途 |

## 3. 已核对的控制调用链

```text
resume_from_snapshot_config
  → from_snapshot_config
  → start
      → start_nowait → start_resume
          → 检查 ublk 可用，准备磁盘、网络与 Firecracker
          → init_envd_instance（只是创建宿主客户端对象）
          → acquire_shared_mem_device（普通路径）
          → load_snapshot_file(..., resume_vm=false, ...)
          → 补充新挂载卷、MMDS、磁盘限流配置
          → fc_instance.resume()
      → wait_for_ready（等待 Guest envd）
```

load_snapshot_file 通过 PUT /snapshot/load 指定状态文件、BackendType::File、内存设备路径、网络覆盖及 dirty tracking 参数。File 表示文件后端类型，路径在此可以是块设备节点，不限于普通磁盘文件。

加载时 resume_vm=false，使 VM 暂不执行。start_resume 随后完成配置协调，再调用 resume。start 的更外层还等待 envd 就绪；不能把内层 resume 成功、外层 start 成功及每项业务成功混为一个条件。

## 4. 一页 RAM 如何变得可访问

恢复不必把完整内存镜像先复制到 server，再用 process_vm_writev 写进 Firecracker。此版本的主路径是 Firecracker 映射只读内存设备，以私有映射和 COW 提供可写 Guest RAM。

课堂假设：所需页尚未准备，且不考虑预取或已有缓存：

```text
Guest 访问某个 GPA 对应的 RAM
  → KVM/宿主内存管理需要为该页准备实际内存
  → 访问 Firecracker 内存后端映射的相应位置
  → Host 内存 ublk 请求
  → daemon 内 OverlayBD 查询完整逻辑镜像映射
  → 取得对应层的数据，填入宿主页
  → 建立/补齐需要的映射，Guest 继续执行
```

这是数据依赖示意，不是宣称每次访问都按固定顺序触发 Guest 缺页、EPT violation 和 Host 缺页。Guest 页表、EPT、宿主映射是不同机制；所需映射与页面已有时不必重新走慢路径。

RAM 页在物理内存中准备好以后，普通访问仍是 Guest GVA→GPA→HPA；不是每次都经过 daemon 或磁盘。HVA 属于 Firecracker 的宿主映射视角。

## 5. 冷缓存、热缓存与首次写入

| 情况 | 可能发生的工作 |
|---|---|
| Firecracker 映射尚未准备，但同一内存设备的 Host 缓存已有该页 | 可利用缓存准备映射，无需为这些字节再读取物理介质 |
| 内存设备缓存未命中 | 可产生 ublk 请求；OverlayBD 的下层仍可能命中缓存，也可能需要本地 IO 或远程获取 |
| Guest 首次修改仍共享的快照页 | 私有 COW，形成该实例可写的内存内容，底层只读快照保持原值 |
| 已经有该实例的私有可写页 | 后续写入通常不再为每次写复制整页 |

因此“冷”必须说明是哪一层缓存。映射、物理页驻留、缓存命中及 Guest 继续运行是不同状态。源码支持配置启动包预取，实际 IO 可以提前发生；不能把所有读取都归因于 Guest 首次访问。

## 6. 为什么可以共享只读设备

同一快照的多个实例可通过引用计数共享同一内存 ublk 设备，从而复用该设备的 Host 页缓存。课堂示例：A、B 初始可读同一快照页 P；A 修改后获得私有内容 P_A，B 仍读原值。共享的是不可变基础数据，不是让 A 的私有修改直接成为 B 的 RAM。

COW 按页提供语义，但是否在每种底层条件下都执行一次实际整页复制不能一概而论。此处用共享页发生私有复制的常见情形帮助理解。

## 7. 为什么恢复后读文件可能没有 Guest VirtIO 请求

如果 Guest 的文件缓存及必要状态已随 RAM 恢复，普通缓冲读取可能直接命中 Guest 缓存，不产生针对 Guest 磁盘的 VirtIO-blk 请求。但承载这些 Guest 缓存字节的 Host RAM 页若尚未准备，仍可能触发 Host 内存后端的 ublk 读取。

```text
Guest 文件缓存命中 → 访问 Guest RAM → 可能按需读取 Host RAM 镜像
Guest 文件缓存未命中 → Guest VirtIO-blk → Host Guest磁盘后端
```

两条路径都可能与存储有关，但用途和请求发起点不同。

## 8. 自测

答题后补充：按需加载决定页面何时准备，COW 决定私有写入如何与基础数据隔离。二者可以组合，也可以分别存在；不能用“因为 COW”解释恢复后不一定全部驻留。Guest 文件缓存命中不保证承载字节的 Host 页已驻留；即使需要后端请求，也不保证发生物理介质读取。

1. 声明 2 GiB RAM 的 VM 已恢复，envd 健康检查也成功，能否断言全部 2 GiB 已读入物理内存？为什么？
2. A、B 从同一快照恢复，A 将原值 10 改为 20，B 未修改时应该读到多少？只读内存设备应被改成多少？
3. Guest 读取一个已命中文件缓存的文件，Host 却发生了内存快照 ublk 读取，是否矛盾？请区分两类块后端。
