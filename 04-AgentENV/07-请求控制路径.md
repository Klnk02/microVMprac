## 暂停请求与设备请求不是同一路径

本轮只核对 AgentENV 调用 Firecracker 的一段，不宣称已追踪外部 API、调度器和所有生命周期分支。

```text
AgentENV server 内的 FirecrackerInstance::pause()
    → 经宿主 Unix socket 发送 HTTP PATCH /vm，状态 Paused
    → Firecracker 控制 API 接收
    → 内部协调暂停（线程协调细节需另按版本核对）
```

`FirecrackerInstance` 是 server 内管理 Firecracker 的对象，不是 Firecracker 进程本身。`instance.rs` 的 `new()` 创建 UnixSocketClient，socket 路径为工作目录下 firecracker.socket；启动参数通过 --api-sock 指定该路径；pause() 发送 PATCH /vm。HTTP 是消息协议，不表示底层一定走 TCP 或 Guest 网卡。

来源：[固定版本 instance.rs](https://github.com/kvcache-ai/AgentENV/blob/9f62cbe07cebfecf416dc9bdcf497e2a97687644/src/sandbox/firecracker/instance.rs)。

对照：Guest VirtIO 网卡请求由 Guest 驱动发布队列并通知设备；暂停控制请求在宿主进程间发送，不需要 Guest 驱动经 virtqueue 传递。控制返回成功也不自动等于完整快照已持久化。

## 请求、响应与结果

- Guest Python 卡死不妨碍 server 经宿主 Unix socket **发出**暂停请求；Firecracker 或控制接口故障仍可能造成失败或超时。用户已正确回答这一点。
- 暂停成功、后续内存保存失败时，可以说 VM 已暂停，不能说完整快照保存成功。用户已正确区分这两个结果；失败后的恢复或清理策略需进一步核对实现。
- 发送请求、Firecracker 处理、server 收到响应是不同阶段。如果请求超时，可能未送达，也可能暂停已经完成但响应未及时到达；不能只凭超时断言 VM 仍在运行。这是通用故障情形，不代表已经验证 AgentENV 的超时与重试实现。
