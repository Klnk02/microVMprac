# 第 7 课：请求控制路径

关联：[学习计划](00-学习计划.md) · [第 6 课](06-VirtIO描述符队列与通知.md) · [第 8 课](08-启动与就绪.md) · [源码索引](源码索引.md)。

本页整理 2026-10-27 起的对话，2026-11-02 归档时补核单机 pause 的节点 API、orchestrator 和 backend 入口；多节点路由及全部失败分支不在本课范围。

## 1. 先把两条通道分开

| | 控制路径 | 设备数据路径 |
|---|---|---|
| 谁发起 | AgentENV server | Guest 驱动 / 宿主设备线程 |
| 载体 | 宿主 Unix socket（`--api-sock`） | Guest 内存里的 VirtIO 队列 + 通知 |
| 消息格式 | Firecracker REST（HTTP） | 描述符 / avail / used 环 |
| 典型动作 | 配置 VM、pause、snapshot | 读写块设备、收发网络包 |
| 需要 Guest 配合吗 | 不需要 | 需要驱动发布队列 |
| 需要 vCPU 执行吗 | 不需要 | Guest 侧需要 |

`HTTP` 只是消息格式。它跑在 Unix socket 上，**不表示走 TCP、也不经过 Guest 网卡**。

## 2. `pause()` 的接口形状

```cpp
// 形状示意，不是完整签名
FirecrackerInstance::pause()
    → UnixSocketClient 发送
    → HTTP PATCH /vm
    → body: { "state": "Paused" }
```

固定版本 `instance.rs` 中可核对的事实：

| 证据 | 表示什么 | 不能据此推断什么 |
|---|---|---|
| `new()` 创建 `UnixSocketClient` | 控制连接是 Unix socket | 不证明 Firecracker 已启动 |
| socket 路径为工作目录下 `firecracker.socket` | 连接目标由 server 决定 | 不代表任何 TCP 端口 |
| 启动参数带 `--api-sock` | 同一路径交给 Firecracker | 命令行参数不等于已生效 |
| `pause()` 发送 `PATCH /vm` | 请求语义是“改 VM 状态” | 不证明 vCPU 已全部停下 |

`FirecrackerInstance` 是 server 进程里的对象，`pause()` 是 server 调用自己的对象，由它经 socket 发请求。**函数名不意味着调用者进入了 Guest。**

## 3. 为什么控制请求不走 virtqueue

宿主暂停控制接口不要求 Guest 驱动主动配合。注意 Python 卡死不等于 Guest 内核或驱动停止；下面考虑的是 Guest 整体无法继续协作的场景：

```text
Guest 内核或驱动无法继续协作
    → 若暂停依赖 virtqueue，宿主就无法让 VM 停下
```

而暂停的用途之一恰恰是“Guest 不配合时也能停住它”。所以控制面必须满足：

- 在宿主进程之间完成，不依赖 Guest 调度；
- 载体是宿主 fd/socket，不依赖 Guest 主动处理队列；宿主资源耗尽、Firecracker 故障等仍可能影响它；
- 请求的解析与执行由 Firecracker 自己负责。

对照第 6 课：Guest 网卡请求要经过 virtqueue，因为那是**设备数据**；暂停是**生命周期控制**，两者路径不同。

## 4. 请求之后有三个结果

| 结果 | 含义 | 能推出什么 | 不能推出什么 |
|---|---|---|---|
| 请求已发出 | 本地写完 socket | 无 | 对方是否收到 |
| 收到暂停成功响应 | 该接口报告暂停操作成功 | 按接口语义确认暂停；部署异常另行诊断 | 快照已持久化 |
| 暂停确认完成 | 所有 vCPU 不再执行 Guest | VM 已暂停 | 内存已保存 |

超时的三种可能，不能只凭“超时”判断 VM 还在运行：

1. 请求根本没送达；
2. 已执行成功，但响应没回来；
3. 正在执行，尚未完成。

要判断真实状态，需要另找证据（查询、日志、观察），而不是把超时当成状态本身。

## 5. 暂停成功但快照失败

| 组合 | 可以说什么 | 不能说什么 |
|---|---|---|
| 暂停成功 + 内存保存成功 | 这两步成功 | 状态、磁盘层、索引、元数据及持久化都完整，快照已验收可恢复 |
| 暂停成功 + 内存保存失败 | VM 已暂停，快照未完成 | “快照保存失败等于 VM 没停” |
| 暂停超时 | 状态未知 | “VM 还在运行” |

用户已正确区分“暂停成功”与“后续快照保存失败”。失败后的回滚、清理、重试策略需要进一步核对实现，本课不下结论。

## 6. 边界与未核对项

- 已补核：下节所列单机节点 API 到 backend 的 pause 主入口；未审计调度器、多节点及全部恢复分支。
- 未核对：Firecracker 内部暂停协调、超时与重试的实现。
- 不要把 `PATCH /vm` 简化成“发个命令就停”；暂停是请求—确认过程（见第 5 课）。
- 控制请求不依赖 Guest，但**依赖 Firecracker 进程和 socket 可用**；这两者故障时请求会失败或超时。

## 7. 答题证据与待验证项

- 用户正确回答：Guest 里 Python 卡死，不妨碍 server 经 Unix socket 发出暂停请求。
- 用户正确区分：暂停成功 ≠ 快照保存成功。
- 待答：请求超时但 Firecracker 实际已暂停时，能否仅凭超时判断 VM 仍在运行。
- 未进行端到端实验；源码核对不等于部署实测。

## 8. 本课检查

1. server 发出暂停请求后超时，但 Firecracker 实际已暂停。能否仅凭超时判断“VM 仍在运行”？
2. 暂停返回成功、随后内存保存失败，应该怎样描述当前状态？

## 归档补充：单机控制调用链与两种 pause

固定提交已核对的简化链路：

```text
客户端 HTTP POST /sandboxes/{id}/pause
    → 节点 API impls/sandbox.rs::sandboxes_sandbox_id_pause_post
    → orchestrator::pause_sandbox → pause_sandbox_inner → pause_sandbox_impl
    → 运行时 handle 的 SandboxBackend::pause(artifact_root)
    → FirecrackerSandbox 的捕获流程
    → FirecrackerInstance::pause：Unix socket PATCH /vm
```

节点 API、orchestrator、backend 接口主要是 **server 进程内部的模块与调用**；直到 Unix socket 才是通向独立 Firecracker 进程的通信。trait 是接口约定，不是额外进程。

外部 AgentENV pause 与低层 Firecracker pause 的范围不同：前者组织状态变更、产物捕获与持久化等流程；后者控制 VM 暂停。因此“Firecracker 暂停响应成功”不能直接充当“AgentENV 外层 pause 全流程成功”。源码还存在可恢复/终止错误区分及持久化失败后的恢复尝试，细节留第 23 课。也不能将原地暂停资源仍在的模型推广到外层 pause 的所有资源回收策略。
