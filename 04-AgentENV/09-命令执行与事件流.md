## 1. `exec` 的接口形状

```text
Executor::start_process_inner
    ├─ cmd        "python"
    ├─ args       ["hello.py"]
    ├─ envs       环境变量
    └─ cwd        工作目录
         ↓ 打包成 StartRequest
    envd 的 gRPC ProcessClient.start
         ↓
    返回响应流（Start / Data / End）
```

两个形状上的事实：

- **命令与参数分开传**，不假设任意字符串自动经 shell 解析（没有 shell 就没有管道、通配符、重定向语义）。
- `start` 返回的是**流**，不是一次性的结果结构；调用方必须持续消费到结束。

## 2. 三种事件的语义

| 事件 | 携带 | 说明什么 | 不能说明什么 |
|---|---|---|---|
| Start | Guest 内 PID | 进程已创建 | 命令会成功 |
| Data | stdout / stderr 分段 | 有输出 | 成功或失败（两个通道都可能写） |
| End | exit_code | 进程已退出 | 业务结果正确 |

```text
时间轴：
start 请求 → Start{pid} → Data{...} → Data{...} → End{code}
```

一个进程可能没有任何 Data（无输出），也可能有很多条；课堂示例只用一条，不代表固定条数。

## 3. `wait` 的判定逻辑

`ProcessHandle::wait` 消费事件流，边收边处理：

```text
循环读事件
    ├─ Data → 追加到 stdout/stderr 缓冲，可触发回调
    ├─ End  → 记录 exit_code，返回 ProcessOutput(Ok)
    └─ 流结束但没收到 End → 返回错误
```

所以存在两个独立的判断：

| 判断 | 结果 | 说明 |
|---|---|---|
| 是否收齐事件 | Ok / Err | 传输与协议层面 |
| exit_code 是多少 | 0 / 非零 | 程序层面 |

`wait` 返回 Ok 只说明“成功取得了结果”，**不代表程序成功**。

## 4. 为什么不能拿 Start 当成功

Start 事件只证明“进程被创建出来了”。之后仍可能：

- Python 已启动但脚本不存在，或脚本运行中出错（退出码非零）；可执行文件本身无法启动时也可能直接返回启动错误，不能保证先有 Start 再有 End；
- 运行中崩溃；
- 权限、路径、环境问题导致失败；
- 被超时终止。

判断成功至少要同时看：`wait` 返回 Ok、收到 End、exit_code 符合预期。

## 5. 输出通道不判结果

stdout/stderr 是**输出通道**，不是**结果通道**：

- 程序可以往 stderr 写警告后以 0 退出；
- 也可以没有任何输出但以非零码退出；
- 把“有输出”当成功、把“stderr 有内容”当失败，都会误判。

判断依据应是程序约定的退出码与任务实际结果。

## 6. 超时与终止

已核对基线中的 `wait`：

```text
若配置了 timeout：
    tokio::time::timeout 包住“收集输出 + 等 End”
超时后：
    经 envd 发 SIGKILL 尝试终止
    忽略这次清理尝试的错误
    返回超时错误
```

三点不能混：

- **超时 ≠ 已确认 Guest 进程终止**；
- **发出 kill ≠ kill 成功**；
- 它也不是从进程创建开始计时的完整生命周期期限（只覆盖等待结果这一段）。

## 7. PID 与身份

- Start 事件里的 PID 是 **Guest 内 PID**，用于后续向 envd 选进程；不能拿去宿主 `ps`、`kill`。
- 宿主上看到的是 Firecracker 进程；Guest 进程由 Guest 内核管理。
- 同一数字在不同视角下含义不同，定位对象时要先问“这是哪个内核的编号”。

## 8. 边界与未核对项

- 未追踪：Guest 内 envd 创建进程的实现、不同 envd 版本的协议差异。
- 未核对：输出背压（大量输出时是否限流）、Data 回调的线程上下文。
- 已核对 wait 中存在累计输出大小上限，超过即返回错误；这不等于已经核对完整的背压或限流机制。
- 源码核对不是服务器实测；超时与 kill 的实际行为未在真实 microVM 验证。

## 9. 答题证据与待验证项

- 已讲解：Start、Data、End 的分工；`wait` 的两种失败（流断、超时）。
- 用户正确回答：超时且终止请求失败，不能断言 Guest 进程已经退出。已讲结果未知时重试可能重复执行，追加文件/外部交易等需考虑幂等。
- 待答：收到 Start 并拿到 PID，能否确认命令执行成功。
- 未进行真实 microVM 命令执行实验。
