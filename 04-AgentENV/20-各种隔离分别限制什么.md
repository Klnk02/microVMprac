# 第 20 课：各种隔离分别限制什么

2026-11-11。本课先定威胁模型，再逐层定位：KVM/硬件虚拟化、namespace、cgroup v2、seccomp-bpf、capabilities、LSM、jailer 各管哪一段。

证据边界：本轮本机无外网、WSL 返回 `WSL_E_ACCESSDENIED`，无法取 AgentENV 固定提交源码，也没有跑任何实验。机制对照使用本机可读的另一份实现——本地 E2B 自托管代码（`D:\SandBox`，VERSION `0.1.4`，随附 Firecracker `1.12.1` 源码与 seccomp 过滤表）。**它是 E2B 的启动配置，不是 AgentENV 基线 `9f62cb` 的部署事实**；AgentENV 自己的 Firecracker 启动参数、是否用 jailer、是否有 cgroup 限额，本轮标记待核对。

## 1. 先定威胁模型：四个场景，四道不同的门

| 场景 | 谁在作恶 | 它已经越过哪道门 | 真正拦它的是 |
|---|---|---|---|
| A. Guest 里跑恶意程序、Guest 内 root | Guest 内的 root 用户 | 什么都没越过，Guest root 本来就能在 Guest 内任意 syscall | Guest 自己的内核（RLIMIT、pid_max）；对宿主而言由虚拟化边界挡住 |
| B. VMM（firecracker）进程被攻破 | 已逃出 Guest 的宿主进程 | Guest→宿主的虚拟化边界 | seccomp-bpf、降权 uid/gid、chroot/pivot_root、capabilities、mount/net namespace、LSM |
| C. CPU/内存/进程数超用 | Guest 内任何程序 | 没有越界，走正常虚拟硬件消耗宿主 | cgroup v2（限额）、vCPU 数量、balloon、宿主调度 |
| D. 网络外连/外泄 | Guest 内任何程序 | 没有越界，走虚拟网卡 | netns + veth + iptables（DNAT/SNAT/REDIRECT）+ 出口代理策略 |

一句话分家：**namespace 改的是「看见什么」，cgroup 改的是「能用多少」，seccomp/caps/LSM 改的是「这个进程能对内核做什么」，虚拟化改的是「这台机器有几个」。** 四者互不替代。

## 2. 位置图：约束发生在谁身上

```text
Guest 内用户程序
   │ syscall（read/write/fork/exec…）
   ▼
Guest 内核          ← A 类被限制在这里；宿主 seccomp 完全看不到这些 syscall
   │ vCPU 执行，必要时 VM-Exit
   ▼
KVM（宿主内核）      ← 硬件虚拟化边界：Guest 只能通过 VM-Exit 影响宿主
   │
   ▼
firecracker 用户态进程（宿主）  ← seccomp 生效点、cgroup 记账点、
   │                              它所在的 netns/mountns 视图
   │ 宿主 syscall
   ▼
宿主内核            ← capabilities / LSM / cgroup 控制器真正执行的地方
```

关键：**seccomp 过滤的是 firecracker 线程发出的宿主 syscall，不是 Guest 程序发出的 Guest syscall。** Guest 里 `read(2)` 一万次不会触发任何宿主 seccomp 规则；而 vCPU 线程的 `ioctl(KVM_RUN)` 会。这就是为什么 Firecracker 的过滤器要按线程类别分开写。

## 3. 每个控制点三问（挡住什么／漏什么／代价）

| 控制点 | 挡住什么 | 漏什么 | 代价 |
|---|---|---|---|
| KVM / VT-x、EPT | Guest 内核与用户态的一切恶意行为，只要不走设备 | 设备模型（VirtIO 后端）、VMM 解析 Guest 输入的代码路径 | VM-Exit 开销、内存二倍页表 |
| vCPU 数量 + balloon | 计算被占满（Guest 想跑满只能占它自己的 vCPU） | Guest 用少量 vCPU 做大量 IO、宿主机时被抢占 | 配置不灵活，扩容要改 VM |
| cgroup v2（cpu.max/memory.max/pids.max） | 宿主侧资源超用、OOM 影响面、宿主 task 数 | Guest 内部限额语义（Guest 有自己的 memcg）；只记账不限额时什么也挡不住；**`pids.max` 只数宿主 cgroup 里的 task（即 VMM 线程），Guest 内 fork 出的进程不是宿主 task，挡不住** | 每沙箱建目录、统计读取开销 |
| mount namespace | 改的是「能看见哪些挂载」，`mount --make-rprivate` 阻止挂载事件外泄 | **不改权限**：namespace 里的 root 仍是 root，可以再 mount | 极低（微秒级） |
| network namespace + veth | Guest 只能看到自己那张网卡与路由表 | 出站仍可全通，除非另有 iptables/代理 | 每沙箱一对 veth + 若干 iptables 规则，运维复杂度线性增长 |
| user namespace | 让 root 在 ns 内没有宿主特权（配合无 CAP_SYS_ADMIN） | 内核 userns 攻击面本身很大 | 兼容性问题，某些内核特性不可用 |
| seccomp-bpf 白名单 | VMM 被攻破后的 syscall 面（提权、加载模块、开新设备） | 允许列表内的滥用（如 `open` 打满 fd）、参数级过滤弱 | 每次 syscall 过一次 BPF（纳秒级）；**升级 VMM 用了新 syscall 会被 trap 杀掉**，运维坑 |
| capabilities drop | 保留 root uid 但不给 CAP_SYS_ADMIN 等能力 | 内核漏洞提权 | 几乎为零 |
| LSM（AppArmor/SELinux/Landlock） | 按路径/端口限制 VMM 能碰的文件 | 需要策略维护；Landlock 只覆盖文件与网络端口 | 策略调试成本 |
| jailer（chroot + uid/gid + rlimit + netns） | 组合拳：降权、限制可见文件系统、限制 fd/文件大小 | 仍需 seccomp 兜底；chroot 不是安全边界（需 pivot_root） | 冷启动要准备 chroot 目录与设备节点 |

## 4. 拿真实实现对照：本地 E2B 自托管 0.1.4 + Firecracker 1.12.1

启动命令（`packages/orchestrator/internal/sandbox/fc/process.go`）：

```text
unshare -m -- bash -c "mount --make-rprivate / &&
   mount -t tmpfs tmpfs <sandbox_dir> -o X-mount.mkdir &&
   ln -s <host_rootfs> <sandbox_dir>/rootfs &&
   ip netns exec <ns-id> <firecracker> --api-sock <sock>"
```

逐条对照：

| 观察 | 事实 | 意味着 |
|---|---|---|
| `unshare -m` | 只有 mount namespace，没有 user/pid ns | 只隔离挂载视图，root 权限不变 |
| `Setsid: true` | 新会话 | 与隔离无关，是为进程组管理 |
| 无 jailer | 没有 chroot、没有 uid/gid 降权、没有 rlimit | 若 VMM 被攻破，攻击者以 orchestrator 的权限（通常 root）行动；B 类只剩 seccomp 一道 |
| `ip netns exec` | 网络视图隔离 | D 类靠它 + iptables |
| cgroup | `/sys/fs/cgroup/e2b/sbx-<id>`，读 `cpu.stat`、`memory.current`、`memory.peak` | **只记账**；`CLONE_INTO_CGROUP` 那几行被注释掉，没有 `cpu.max`/`memory.max` 写入 → C 类无硬限额 |
| seccomp | Firecracker 自带过滤器：`vmm` 60 条、`api` 35 条、`vcpu` 43 条，三组 `default_action: trap`、`filter_action: allow` | 白名单制；**未做自定义裁剪，用上游默认** |

Firecracker 1.12.1 的默认过滤器是「按线程类别的最小允许集」，默认动作 `trap` 意味着命中未允许 syscall 时进程收到 SIGSYS 直接死，而不是返回 EPERM。这解释了为什么升级 Firecracker 版本常需要同步更新过滤器：新代码引入新 syscall，旧过滤器会当场 trap。

结论：**安全设计建议（Firecracker 官方 prod-host-setup + jailer）≠ 实际启动配置。** 同一份代码里，设备池、网络池做得挺讲究，而 VMM 的降权和资源限额是缺的。这正是「三问」该问的地方：它挡住的是「Guest 与宿主之间」，漏掉的是「逃逸之后的横向移动与服务中断」。

## 5. 容易错的三个点

1. **seccomp 拦不到 Guest。** Guest 的 syscall 由 Guest 内核处理，与宿主 seccomp 无关。seccomp 只在 VMM 自己发宿主 syscall 时生效。
2. **namespace 不是权限。** root 在 mount ns 里仍是 root，可以 `mount` 覆盖任何它有权挂的东西；真正的降权得靠 user ns、caps、uid 切换。
3. **Guest 内 fork bomb 不会出现在宿主进程表。** 宿主只看到 firecracker 的固定几个线程。Guest 内被 Guest 内核的 `pid_max`/`RLIMIT_NPROC` 限制；**宿主侧兜底不是 `pids.max`**（它只数宿主 task，Guest 进程根本不在宿主 cgroup 里），而是 `memory.max`、`cpu.max`、vCPU 数量与 balloon —— 也就是说 Guest 想搞死宿主，靠的是吃资源，不是增加进程数。
